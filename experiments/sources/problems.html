sources: what the first try found

The experiment in experiments/sources builds the sketch from ermine-plans/sources-2026-10-22.tex: a holder, a link that syncs two holders, a value mirror, and the smallest history to name writes. Nothing here is decided. The picks it made are in plan.org. "What it might take" is the experiment's guess, not a choice.

in the graph

  1. A removal has no change header.

    table.del(part, id) takes no header, so a removal leaves the graph with no actor, time or site, though every write from outside is meant to carry its site. The history makes one up: time now, actor null.

    core/table/typescript/table.ts (del); history.ts

    done on main (10-23): places makes the header from the open scope when told of the removal, its site the caller of table.del, in TS and C

  2. History has to be there from the graph's first write.

    Merging writes made at once replays the part's whole history. The table can't list ids, so a history started on a graph that already has values has no base and can't build one.

    history.ts; plan.org's "made before the graph's first write"

    a base write for what's there when the history starts, or a way to list ids

  3. A fact's values change after it's told.

    Places writes children through unread, in place. A holder that held a fact's patches as given would see them change, and their names would stop matching. So the history copies when it names and when it lands, against "share, don't copy", for this one use.

    write.ts (a named write is read back from its encoding)

    nothing, if a copy at naming is fine; else facts that don't change once told

  4. Telling your own writes from others' is by guess.

    While a write lands, the history ignores every fact at that node and part as its own echo. A watcher that writes there in the meantime loses its write. Places gives no clean way to say "this fact came from my commit": the entry works for add and update, but not for del.

    history.ts (echo); scenario 02

    a mark on a fact saying which commit made it

in holders and links

  1. drop and since don't fit together.

    After a holder drops a node, the link still thinks that holder has those writes, so it never sends them again. Later writes on that node are refused for missing parents, and only a new link repairs it. When the history drops a node, its next local write has no parents, so the node gets a second, unrelated history. The sketch doesn't say what the other side learns from a drop.

    scenario 09

    a drop the link is told of; history keeping its heads after a drop

  2. Refused is two different things.

    Some refusals are for good (a misnamed write, the holder's own say). Others are for now (the disk is full, a parent was dropped). The link can only skip a refused write or stall; it skips, so a temporary failure is lost on that link.

    scenarios 10, 11

    a "not now" outcome beside "refused"

  3. An opaque cursor can't move partway.

    When some writes in a batch are refused, the cursor moves past all of them or none. The same opacity means the link's sets of known names can't be trimmed; they only grow.

    link.ts; scenario 12

    a cursor per write, or one a link can compare

  4. A holder that can't list has nothing to act on when poked.

    A poke means "since would give something new", but this holder has no since. The link can only fetch nodes it already asks about.

    scenario 13

    a poke that names the node

in files and the mirror

  1. Two processes saving one file: the last save wins.

    With only read, write and watch, two saves at once lose one. The holder reads the file again before each save, which narrows the window but doesn't close it. The sketch already makes two devices on one file the host's.

    file.ts; scenario 04

    a compare-and-swap (or etag) on write

  2. The mirror writes the whole value.

    A hand edit and a write elsewhere made at once can't merge; one of them is lost whole. The mirror makes plain writes, so it could diff into string patches without that becoming protocol.

    mirror.ts; scenarios 05, 06

    a diff into patches

  3. The mirror wrote over a save it hadn't heard yet.

    A person saved the file, a graph write landed before the watch said so, and the mirror wrote over the save, which was then in no history. Now every write is checked: the file must still hold what the mirror last read or wrote. If not, nothing is written, the file is read in at once as a hand edit, and the mirror's node says "the file changed since I last looked: not written; read in". The same rule covers a file deleted or renamed by hand (nothing written while it is gone), a file that isn't UTF-8 (nothing written until it is), and a write that throws (tried again after a second, doubling to a minute, and on each new value).

    mirror.ts, access.ts; scenarios 14, 15, 16

    fixed, with a window left: a save landing between the last look and the rename (Deno) or close (web) is still written over. Closing it needs a lock an editor takes. Reading in on a refusal also means the save becomes the value; the graph's write is only in history.

  4. Two mirrors on one file tie their nodes.

    A mirror is a process at /system/mirrors/<the file's name>, so a second mirror of the same file name is refused by start ("taken") and nothing is made. One file under two names (a symlink, a second path), a mirror put at another path, or a mirror in another process is still not seen: opening the second writes the file's value over its node, and after that the two nodes move together.

    mirror.ts; problems_test.ts; scenario 17

    a lock on the file, again

shown in the graph

  1. Trouble, link status, refusals and the skipped count lived on JS objects.

    A mirror and a link are now processes (ermine/processes' start, with nothing changed there), at /system/mirrors/… and /system/links/…. Each gives a computer whose value is its state, a code and its words, such as { code: "changed-not-written", words: "the file changed since I last looked: not written; read in" }. That value is the process node's value, and its status is that computer's, so PENDING goes at its first run. What it has (the file, the node mirrored, values not written, names known, refusals) is in the node's attributes. The history has no state that changes, so it keeps its one record (facts skipped) on a node of its own. A computer reading any of these runs again when they change. The host's rule leaves all of them, and the processes' rows, out of the history, so they are never sent.

    status.ts (the codes, listed once); scenario 17

    fixed. Left: the file holder's trouble reading its file is still on the object.

  2. A process needs a computer to stop saying it is pending.

    start writes ermine.computer.status PENDING on every process's node, and only a given computer's run ending takes it off. A mirror and a link give a computer of their state, so that fits. The history would only have a computer of a constant to give, which is why it is not a process.

    ermine/processes/typescript/start.ts; status.ts

    nothing, while every process has a state worth computing

what held up

  • The history is itself a holder, so the graph's side of a link is one more holder, with no special case.
  • The mirror and the history record each other's writes, with no coordination between them, as the sketch expected.
  • The split into holder, link and mirror held. Writes did need to say their node and part, as the reviewer said.
  • put never throwing was easy. The link also catches a put that throws and counts it as refused.
