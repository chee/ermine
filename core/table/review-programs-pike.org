A review of the program sketch (plan.org, "starting a program", 10-15) through a Plan 9 /
Inferno / Unix / Go lens. The opinions are the lens's. None of this is decided. Grounded in
plan.org and playground/ermine-slaygrounds/examples/prog-build (host.ts: collect, chain, build;
program.ts). Sources at the end.

* In short
- One short word for a form of code. A handler is named by the form it takes, the same word.
  Chaining is then one lookup per step. No type graph, no search, no ties.
- Capabilities are nodes you can reach from inside your box. If you can reach it, you can use it. A
  needs list is a label for people, never a gate.
- Compiling makes a computed node, cached by hash of the compiler and the input. ermine already is
  mk.
- Resolve once, at start. Write down what was used. That record is the pin.

"Data dominates. If you've chosen the right data structures and organized things well, the
algorithms will almost always be self-evident." (Notes on Programming in C, rule 5)

* 1. What's needless
The sketch has six words (type, needs, from, to, runs, gives) for two ideas: what the code is, and
what it may touch.

- =from= / =to= with a search over them. prog-build's =chain()=: fewest steps, a tie to the
  nearer loader, a =tried= list to explain dead ends. That is a solver, and a solver always leaves
  you asking "why did it pick that?". Name the handler for =c= "c" and the algorithm is lookup. Go
  has no dependency solver either: go.mod is a list you can read.
- =type= and =from= on a compiler. With handlers named by what they take, the name is =from=.
  Keep =is= (how it runs) and =makes= (what a compiler gives).
- Two names for one form: =com.netscape.javascript-source= and =party.chee.ermine.js-main=. This
  alone stops the chain at the bottom (§6.1).
- =js-main= glues two facts together: the form (js) and a device (the DOM, which only the main
  thread has). Split them.
- =runs: [...]=. A host runs one form. Plan 9's exec(2) takes "a valid binary image ... for the
  current machine architecture, or a shell script" (=#!=). Nothing else. Everything is built from
  those two.
- =gives: [...]= on the host. A host gives something by placing it. A list next to the placements
  says the same thing twice.
- UTIs (§4).

How Plan 9 runs "this program, here":
| Plan 9 / Inferno     | what it does                                       | ermine                                   |
|----------------------+----------------------------------------------------+------------------------------------------|
| exec(2)              | runs this machine's binary format, or =#!=         | the host's handler at the root: the bottom |
| =#!/bin/rc=          | the file names its runner, by name                 | =is: "c"=                                |
| /bin, a union        | "/mips/bin ... bound to the conventional location /bin"; no $PATH | lookup up from the place: the union is the ancestry |
| per-process namespace | what's bound is what exists                       | the box                                  |
| Dis (Inferno)        | one portable form, run natively or hosted          | the one form every ermine host runs      |
| mk                   | building, separate from running                    | the scheduler: computed nodes            |

Dis is the biggest lesson. N languages compile to one form, and M hosts run that form: N + M,
not N × M chains. For ermine's hosts today (browser, deno, JSC on the Mac) that form is an ES
module whose default export takes the process's context. Wasm is the likely second one for small
devices. Chains are then short, mostly one step: source → the form.

* 2. Capabilities: files, not needs
- Plan 9: if /net is in your namespace, you can use the network. If it isn't, you can't, and
  nothing checks a list. =rfork(RFNOMNT)=: "subsequent mounts into the new name space and
  dereferencing of pathnames starting with # are disallowed". You keep what you were given.
- Inferno =pctl(NEWNS)=: "the current directory is made the root directory, /, of the new name
  space". That is ermine's box (a root and a cwd) almost word for word. =NODEVS= closes the rest.
- Per-process devices: "there are many instances of /dev/cons, each served by 8½ to the local
  name space of a window" (names). ermine: each process gets its own =dom= node under the same name.
- Override by binding: =import helix /net= uses another machine's network. ermine: place a
  gateway's =fetch= at /work/fetch, and everything under /work uses it (nearest wins).

Which fits "only reachable exists" and the box: reachability. It is already the gate. Declared
needs plus a host check would be a second mechanism next to it, and two mechanisms drift apart.

- =fetch=, =dom=: nodes the host places (a host function as the value; never saved). A program
  reaches them by lookup inside its box.
- =es2025=: not a capability. It is the form, or the form's version. It goes on =is=, or nowhere
  until it breaks something.
- =needs=, if it stays: shown, not checked. Better still, derived. A wasm module lists its imports
  (=WebAssembly.Module.imports=). A run's reads list what it reached, each with =from=. What you
  observe can't drift; what you declare can.

The catch: in JS, =fetch= and =document= are globals. prog-build's sneaky.js reaches
=globalThis.ermine= and =fetch= anyway. A capability node is only real if the js runner
evaluates programs without ambient globals (a worker with them deleted, or SES-style
compartments). Dis has no way out except devices, and that is what made Inferno's namespace a real
wall. Until the runner does the same, nodes-as-capabilities are a convention, and so is any needs
check.

Against chee's words: "a program is a node that declares what it needs and provides" (decided)
becomes: it declares what it *is*; what it needs, it reaches; what it provides, it places. "a
program runs on a platform": yes, and the platform is =is=. "maybe the capability and the code
lang stuff needs to be split": yes. Split them exactly as Plan 9 does: $cputype for what runs, the
namespace for what you can touch.

* 3. The compile chain
Plan 9 has three tools for three jobs:
- =#!=: how to run a file. One hop, by name, resolved in the namespace of the process doing the
  exec.
- mk: how to make a file from other files. "Mk performs transitive closure on metarules", so mk
  does build chains. But "There must be only one way to build each target". Ambiguity is an
  error ("ambiguous recipes"), never a tie-break. And "Mk avoids infinite cycles by evaluating each
  metarule once."
- the namespace: which build is in effect here. =objtype=mips mk= builds for MIPS. "The first line
  causes mk to include the contents of /$objtype/mkfile." One variable picks the target, the same
  way GOOS/GOARCH do in Go.

For ermine:
- the chain: =#!= applied to compilers too. Named handlers, one lookup per step. Ambiguity can't
  happen, because a folder holds a name once. If the search stays, take mk's rule: two chains is an
  error that shows both, not "fewest steps, nearest wins".
- the build: a computed node. Tracked reads are mk's prerequisites, and an equal result stops
  further work (early cutoff; mk's =P= attribute, done right). ermine is the build system. In
  "Build systems à la carte" terms, prog-build already uses constructive traces.
- the target: the place. Building for a mounted device means loading from a place on that device.
  Like GOARCH, it is one argument, not a type graph.
- caching: Go's way, not mk's. mk writes =.8= files next to the source. In ermine the source may be
  synced, so a laptop's =clock.c/wasm= and a phone's would collide. Go keeps a separate cache
  (GOCACHE) that "correctly accounts for changes to Go source files, compilers, compiler options",
  and that "does not detect changes to C libraries imported with cgo". The lesson: anything a
  compiler reads that isn't in the key gives you a stale cache.
  - key: hash(the compiler as it ran) + hash(input) + the form made.
  - where: a host-local folder (=/cache/<key>=), never saved, never sent. Visible and deletable.
  - a compiler is pure: input in, output out. One that calls a server (prog-build's =cc= →
    =/compile=) is the cgo case: the server's version goes in the key, or you rebuild by hand.

* 4. UTIs vs a magic line or a suffix
- "If C++ and Java are about type hierarchies and the taxonomy of types, Go is about
  composition." (Less is exponentially more.) UTIs are a taxonomy: reverse-DNS names plus
  conformance (=public.c-source= → =public.source-code= → =public.plain-text=). If ermine uses
  conformance, every lookup becomes a hierarchy search. If it doesn't, the long names buy nothing.
- The tell: the type that matters most, the host's form, had to be made up
  (=party.chee.ermine.js-main=). A registry whose most important entry you write yourself does
  nothing for you.
- Plan 9 has no file types. Content decides (a.out header, =#!=). Suffixes are a convention that
  mk and the plumber match, at the point of use, by pattern: =data matches
  '([a-zA-Z0-9_\-./]+)\.(jpe?g|gif|bit|tiff|ppm)'=.
- A suffix doesn't work in ermine: names belong to slots, not nodes. One node under two names would
  have two types.
- A magic line in the value doesn't work either, because values aren't only text (wasm bytes).
- So use an attribute, which is the node's own data and the closest thing to a magic number. Keep
  it short: =is: "c"=. The same word names the handler, =bin/c=.
- Keep UTIs at the edge. The files program maps a Mac file's UTI or suffix to =is= once, on import.
  "Which app opens this" (the UTI's real job on the Mac) is plumbing: rules in a node that match
  and send. It is not a type on every program.

* 5. Pids in paths
- Plan 9: "one directory per live local process, named by its numeric process id". The kernel
  creates n. =/proc/n/ns= is "a textual representation of the process's file name space";
  writing =kill= to =/proc/n/ctl= kills it. A process's name is kept apart from where it works.
- ermine decided the other way: a process is at a path, it has one path, and a start is refused
  where one is already running. So the path is the name, and =pid("clock")= is not a pid. It is a
  free name, chosen before =start=:
  - two starters both read /work and both choose =clock-2=, and one is refused. Kernel pids can't
    race, because choosing and creating happen in one step.
  - simpler: =start(program, root, path)= either gets the path or is refused. A helper that retries
    with =clock-2=, =clock-3= is a library function (mktemp). It isn't core, and it isn't called
    pid.
- =ps=: Plan 9 gets it from =ls /proc=. ermine's processes are scattered across paths, so the
  host's process rows should be listable as one folder (derived, for showing).
- What to keep from /proc: =ns= (the record of what was resolved, §7) and =ctl= (stop by writing
  to the process's node, =./on/stop=).

* 6. What breaks first
1. The bottom. =wasm-js= is =com.netscape.javascript-source=, but the host runs
   =party.chee.ermine.js-main=. Nothing runs javascript-source, so wasm-js can't run, so cc-wasm
   (wasm) can't, so clock.c can't. The very first run fails. Fix: give the host's form one name,
   and treat a node with no =is= as a host function. The recursion ends there.
2. Ties. Put two c → wasm compilers (clang, zig cc) in one folder. prog-build breaks the tie by
   directory order, but children are a map (lean) with no order, so two devices can pick
   differently. With named handlers, a tie can't exist.
3. Re-resolving under a running process. A tracked plan reruns when a nearer handler or key shows
   up. Drop a =c= into /work and every C process under /work rebuilds, and maybe restarts. Plan 9
   resolves at exec; binding a new /bin/date doesn't touch a date that is already running.
4. Loops. A C compiler written in C has =is: c= and handles =c=, and recurses forever. Plan 9 and
   Go bootstrap from compilers that are already built. Needed: a check for a form already seen, and
   a pinned cached build of the compiler.
5. The fake wall. =needs: []= passes the check, and the JS reaches =fetch= anyway (§2).
6. Drift. Someone writes =needs: ["fetch"]= by hand, and the code also touches =dom=. The check
   passes and the run fails, or the other way round.
7. Which walk. prog-build walks from where the program /sits/; the sketch walks from where it
   /runs/. Under prog-build's rule, moving clock.c changes how it compiles. Plan 9 resolves =#!= in
   the namespace of the process doing the exec. Walk from where it runs.
8. Cross-device. Start at a place on a mounted microcontroller, and lookups fall past its root into
   the laptop's /bin unless a box stops them. Worse, a compiler found that way is loaded from that
   place, so clang gets asked to run on the microcontroller. This is $cputype vs $objtype: handlers
   are /found/ from where the program runs, and compilers /run/ where the builder is. That costs
   one more argument (=here=).
9. A stale cache. The compile server's version is not in the key (§3).

* 7. The shape
The host places itself at its root (chee 10-09: "the host might want to place a loader right at
the top of the root that represents itself"):

#+begin_example
/bin/js        value: host fn (js source → runnable)   attributes: {}                          the bottom
/bin/wasm      value: wasm → runnable, written in js    attributes: { is: "js" }                an interpreter
/bin/c         value: cc-wasm (bytes)                   attributes: { is: "wasm", makes: "wasm" } a compiler
/fetch         value: host fn                           attributes: {}                          a device
/dom           value: host fn                           attributes: {}                          a device
/work/clock.c  value: C source                          attributes: { is: "c" }                 a program
#+end_example

There are two attribute words. =is= says how a node runs, and it is the name of its handler.
=makes= says what a compiler gives.

#+begin_src ts
// a node → a host function. handlers found from `at`, up only, nearest first: one name, one answer
function load(x, at, seen = []) {
	const form = attrs(x).is
	if (form === undefined) return x.value // a host function: the bottom
	if (seen.includes(form)) throw new Error(`${[...seen, form].join(" → ")}: a loop`)
	const h = lookup(at, ["bin", form]) // no search: the name is the match
	if (!h) throw new Error(`nothing runs ${form} from ${at}`)
	const f = load(h, at, [...seen, form]) // a handler is a program too
	const makes = attrs(h).makes
	if (!makes) return f(x.value) // an interpreter: #!
	const out = cache(h, x, () => f(x.value)) // a compiler: a computed node, keyed by hashes
	return load({ attributes: { is: makes }, value: out }, at, [...seen, form])
}

// a process: its box, its program loaded once from where it will run
function start(program, root, path) {
	if (running(root, path)) throw new Error(`/${path.join("/")}: one is running`)
	const box = { root, path } // NEWNS: root is its "/", its folder its cwd
	const run = untracked(() => load(program, box)) // resolved once; a re-resolve is a restart
	return run(context(box)) // lookup, read, edit: all inside the box
}
#+end_src

clock.c, step by step: =c= → =/bin/c= (it is wasm, so =/bin/wasm=, which is js, so =/bin/js=, the
host) → wasm bytes, cached → =/bin/wasm= → a runnable. Every step is one lookup that you can read
and draw. Compiling is async and the cache entry is pending while it builds; ermine's colourless
async handles that already.

The box is a folder, and placing into it is bind. To let clock fetch but not touch the DOM:
#+begin_example
/boxes/clock   (its "/")
  bin   → /bin's id
  fetch → /fetch's id
  work  → /work's id
#+end_example
=start(lookup("clock.c"), /boxes/clock, ["work", "clock"])=. =dom= isn't placed, so for clock
it doesn't exist. There is no check to write. With no box given, a process inherits the
starter's root (rfork without RFCNAMEG).

The record is the pin. The process node (never saved) carries what was used, like =/proc/n/ns=:
#+begin_example
/work/clock  attributes: { program: "ermine://<clock.c>/commit/<h>",
                           ns: [["c", "/bin/c", "<id>@<h>"], ["wasm", "/bin/wasm", "<id>@<h>"],
                                ["js", "/bin/js", "host"]],
                           built: ["<key>"] }
#+end_example
- To start as before, start from the record.
- To pin a handler for a whole subtree, place a versioned id in a bin:
  =/work/bin/c → ermine://<cc>/commit/<h>=. That is go.mod, kept in the namespace. No pin feature.
- "a process being able to write its own loader": its =./bin/c= is nearest for anything it starts
  inside itself.
- "which device runs it: whichever device the closest valid loader is on": whichever device's
  bottom handler the recursion reaches.
- "collecting all the secret keys ... so there's no deadend" (10-09): this is where the shape
  differs. Nothing is collected; nearest wins. A dead end is an error that names the form and the
  place, and you fix it by placing or removing something. Plan 9 doesn't try the next member of
  /bin when an exec fails.

"Simple features that interact in simple ways." (Simplicity is complicated.) Here that means one
lookup, two attributes, one cache, one record.
