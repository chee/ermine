* Findings
1. The split by part matches how the data is accessed. A walk reads only children, one name per
   step, 3–11 steps per get. About 85% of content reads use the value alone, and the bytes are in
   the value. *fact*
2. What costs is the table's layout, not the split. Today's index costs about 1 KB per id, more
   than the data itself (773 B). A walk step takes 3.3 µs at 1M ids. With one Map per part it is
   958–1,053 B per id and 0.67 µs, with the same key (part, id) and the same API. *mine*
3. Placing a name copies the whole children map, because update copies on write by default. 10k
   names in one folder take 8.6 s and 30k take 106 s. With cow false a place takes 1.2 µs. Real
   folders reach 24k–77k names. *fact*
4. "The children of /work" are three facts, each with its own key. The names in the shared folder
   live in the node. My overrides are a patch node that I place. A thing at a path on my device
   lives in my root's rows. Nothing that belongs to one asker goes inside a shared node. *mine*
5. Attributes are used by 5 of 79 demos. Metadata and per-viewer state mostly sit as child nodes.
   *fact*

* 2. The parts split, judged on the data
** What it buys and what it costs
| what            | the split buys                                                                                | it costs                                                                                                                      |
|-----------------+-----------------------------------------------------------------------------------------------+-------------------------------------------------------------------------------------------------------------------------------|
| walks           | a step reads one name in one entry and never touches the value's bytes                        | in memory it is one pointer either way; in sync a whole node travels together, but folders seldom hold big values              |
| tracking        | a change spot and a table event per part                                                      | none, but paths.ts already tracks by path inside a value, so the part is one more step at the top and adds no granularity paths lacks |
| attribution     | the latest change per part, as unix keeps mtime (data) and ctime (inode) apart                | one change covers a whole map: who placed each name comes only from sync's history                                            |
| patch nodes     | `at` is that part's version, so a title override isn't made stale by typing (10–60 ops/s)     | a patch over two parts takes two patch nodes                                                                                  |
| fate            | save and send can be chosen per part (process is never saved): 3–6 choices, not a mark per entry | –                                                                                                                          |
| merge           | each commit names its table, so sync can leave a part out                                     | none for conflicts: a CRDT doc would merge per key anyway                                                                     |
| memory          | –                                                                                             | today's index is ~1 KB per id, more than the data; each write's header is ~350 B                                               |
| the whole node  | –                                                                                             | get(id) reads one Map per id today, or 3–6 gets with a Map per part                                                           |

| system      | content                       | metadata                                                          | names                                              | per-asker names                                  | history                            | shared as             |

| WNFS public | a CID to UnixFS blocks        | a CBOR map inline in the node                                     | entries name → CID; dir and file are two types     | none                                             | previous, per node                 | subtree (a private key opens everything below) |
| Automerge   | anything in the doc           | anything in the doc                                               | patchwork's folder doc lists {name, type, url}     | none                                             | per doc                            | doc                   |
| ermine      | value                         | attributes                                                        | children                                           | open                                             | per part, in one sedimentree per node | node               |
- Every system keeps the big bytes apart from a small record. When WNFS keeps "metadata with
  content", the metadata sits with a pointer to the content; the bytes are stored elsewhere.
- Every system keeps names in the parent, as ermine's children do.
- Listing with metadata is hot everywhere. Unix dirents gained d_type, macOS added
  getattrlistbulk, Plan 9 returns stats from a directory read, git keeps mode in the tree, and patchwork keeps type in
  the folder doc. In ermine a listing is N+1 reads. In memory that is under 0.3 ms for 1,000
  children. Over sync, all N nodes must have arrived first.
- Unix and Plan 9 never store per-asker names in the files: the namespace belongs to the process.
- In WNFS private, a folder's key opens everything below it, so "shared with fewer people, deeper
  down" can't be said. Keyhive can say it per doc, but the id stays visible in the parent,
  *decided*: "this isss true".

** Judgement (*mine*)
- Value and children belong apart. Size, readers, write rate and merge all agree.
- Attributes and value are apart by meaning, *decided*: "metadata is not the content of a file". Unix
  splits mtime and ctime the same way. Use of attributes is small so far (5 of 79 demos): demos put
  type and pos in child nodes, which can be tracked, placed and overridden by name. I give no
  verdict on this.
- The cost is in the layout, not the split. The key (part, id) stays and only the storage changes:
#+begin_src ts
// a Map per part, as a structure of arrays: a walk touches only the children Map. same API
const parts = new Map<Key, Map<Id, Entry<unknown>>>()
// an entry's key; a list only when one entry sits under several keys (allowed, *decided*; rare)
const where = new Map<Entry<unknown>, Packed | Packed[]>()
const get = (part: Key, id: Id) => parts.get(part)?.get(id)
// the whole node: 3–6 gets
const node = (id: Id) => [...parts].flatMap(([p, m]) => m.has(id) ? [[p, m.get(id)!]] : [])
#+end_src

** Patch nodes, for Basman's open authorship
- chee 10-14: "Basman-style changing 1 part of something without changing other parts, which i
  think we get from patch nodes attached to other nodes".
- A patch node is {patches, on, at}, *decided*. *mine*: `on` names a part as well as an id, and `at`
  is that part's version.

| part patched | patch shape                  | work to keep it current as the target changes                    |
|--------------+------------------------------+------------------------------------------------------------------|
| children     | {path: [name], value: id}    | none unless the same name changes: other names commute           |
| attributes   | {path: [key], value}         | the same, per key                                                |
| value (text) | ranged patches               | every op on that part after `at` (the anchors library)           |
- Who sees a patch node depends only on where it is placed, *mine*:
  - Only me: my mount points at it (3a). This covers a patch node over a shared folder that only I
    see.
  - Others too: place it as a name inside a folder they walk through. That can be W itself,
    W.children.config → o_c over c (others see the override and c stays untouched), or a shared
    parent.
  - Some of us: share o1 with them, and each of them points their mount at it (7b).
- An override deep inside a folder I don't own copies the path: d patch nodes, where d is its depth
  under my mount (estimated 1–2). Each is about 150 B, and over children maps they cost nothing to
  keep current.
- Reads are lists: entries() gives the row, then each patch node outermost first, then the target.

** The step (*mine*)
#+begin_src ts
// one step for one asker. rows: the asker root's process rows at the path so far (usually none)
function step(at: Id, name: string, rows?: Level): { id?: Id; rows?: Level } {
	const row = rows?.[name]
	const next = isLevel(row) ? row : undefined
	if (isId(row)) return { id: row, rows: next } // the ephemeral wins, *decided*
	return { id: child(at, name), rows: next }
}
// a name in a folder, through a patch node when the id is one
function child(id: Id, name: string): Id | undefined {
	const p = table.get("patch", id)?.value // {on, part, at, patches}: usually nothing there
	if (p?.part !== "children") return table.get("children", id)?.value?.[name]
	const over = last(p.patches, [name]) // the latest patch at [name]
	return over ? over.value : child(p.on, name) // a removal: undefined
}
// every thing at a name, the front one first: [{id, from}] (reads are lists)
function entries(at: Id, name: string, rows?: Level): { id: Id; from: Id | "process" }[]
#+end_src

** Where this strains chee's decisions and principles
- Outer wins was set aside, *decided*: "let's forget outer wins for now". Nothing here walks path
  entries. Rows are read from the walk's own root only, as plan.org already has it: "a walk reads
  only its own root's rows until then".
- 3a needs the path copied for deep overrides (d patch nodes). A table at the root keyed by target
  id would avoid the copying for one get per step. It is close to "a local children part", which was
  in the 10-14 bundle chee called "none of this is right".
- "A name only I want there" gets two keys, 3a (follows where I place it) and 3b (stays at a path).
  chee: "i keep moving around where that choice is made". The data says the key is the choice.
- "a process exists in one place and has 1 path", *decided*: rows by path give this. Whether Juno
  sees it depends on the anchor (W or my root), which is left open: "is there a way to avoid
  answering this".
- Keep per side: "a don't-save flag" was also in that rejected bundle. Here it is a setting each
  side holds, never something on the node. How storage and sync coordinate is *open*.
- Attributes: the usage data is thin. Whether they fit is chee's call.
- "it would be nice to be able to treat a node like it's a real thing", *thought*: with a Map per
  part, a whole node is 3–6 gets.
- Undo keeps the old value, *decided*: "it's not going to be much ram". That holds for the demos
  (values of 4 KB or less). A whole-value set of an N MB image holds 2N MB until the next write.
- 7a leaks the name and the id (Keyhive's own rule). 7b costs one write per member.

** Open
- A rename arriving by sync across a row's route: show the row off its route, or move it.
- Whether sharing a folder shows the processes in it (anchoring the rows at W or at my root).
- What a patch node's `at` is: change identity is still *open*: "it dosn't matter right now".
- Whether listings over sync need summaries of the children.
- Keep and send: how the person, storage and sync coordinate.
