Can Emacs's advice (=add-function=, =advice-add=: =:before=, =:after=,
=:around=, =:override=, =:filter-args=, =:filter-return=) be built on the core
as it stands? Read against GRAPH, SCHEDULER, LOADERS, PROTECT,
WHAT-IS-A-PROCESS (the proposal) and =experimental_layers/processes= (the
prototype). /spec/: the papers say so. /TS/: =core/*/typescript= today.
/ran/: checked with a scratch test outside the repo.

* The shape: a slot is a function cell

| Emacs                                       | ermine                                                         |
|---------------------------------------------+----------------------------------------------------------------|
| a symbol's function cell                    | a slot, such as =@60/on/add=                                   |
| =advice-add=                                | place or move a node into that slot                            |
| the outermost advice runs first             | the first member wins (GRAPH, Paths)                           |
| the advised function, still there           | the members behind, still read (reads are lists)               |
| depth                                       | position in the slot                                           |
| =advice-remove=                             | unplace the id; or its advisor dies and the node is released   |
| =describe-function=: "has :around advice"   | a read of the slot: an item per member, with position, header  |
| advice on a primitive, unseen by C callers  | a wrapper governs only its holders; bookkeeping goes beneath   |
| a function object taken before the advice   | the function =handler()= returns, which calls by node          |

Every combinator is one shape: a member in front that may call the member
behind. =:override= never calls it; the other five do, before, after, or
around, changing its arguments or its result. For a value, the member behind
is =items[1]= of a read, which works today. For a handler it is a call, and
that is the one missing verb.

* 1. Advising a handler: every =add= logged, or its input changed

*SCHEDULER.tex, TS: no.* A handler is a function in the scheduler's table,
by pid and name, called by the host's =fire=. It is no node, so nothing can
be put in front of it. Only the host can advise it, by wrapping =fire=:

#+begin_src ts
const s = schedule(protect(g, may), loaders, { graph: g })
const host: Scheduler = { ...s, fire: (op) =>
  op.process === todo && op.handler === "add" ? s.fire({ ...op, input: trim(op.input) }) : s.fire(op) }
#+end_src

Invisible in the graph; removing it is editing the host.

*The proposal: yes, by placement, but for one verb.* The advisor makes its
own =add= and moves its node in front of the to-do's:

#+begin_src ts
// /programs/trim-adds
export default ({ api, handler, self }) => {
  handler("add", ({ next }, item) => {             // next: missing today
    const out = next({ ...item, text: item.text.trim() })   // :filter-args
    console.log("added", out)                      // :after
    return out
  })
  api.move({ address: ["on"], name: "add", id: `${self}.on/add`,   // its own on (layout B: ./on)
             to: ["/", "docs", "todo", "@60", "on"], toname: "add", position: 0 })

An ephemeral node may leave its one slot for another (GRAPH, Placement), and
the scheduler keeps a handler's function by its node's id, so a moved
handler still answers.

*The prototype, ran: works*, because its nodes are ordinary, so the
original can be mounted under a second name for the advice to call. The
host places both (a program's context has no =place=):

#+begin_src ts

- Cost :: a walk per call; a handler record per piece of advice. Every change
  the original makes carries the whole chain in its agent, so headers grow
  with advice.
- Awkward ::
  - /Calling the original./ In front of it, its path reaches the advice, so a
    call by path recurses. The prototype mounts the original elsewhere. Under
    the proposal a handler node sits under an ephemeral process node, so it is
    ephemeral and cannot be mounted anywhere else (=one-place=): the member
    behind cannot be reached.
  - /The world function goes around the advice/ (ran). What =handler()=
    returns calls its node by id, so a DOM click never meets the advice; only
    a call by path does. In Emacs: a key bound to a lambda, not to a symbol.
  - /The owner must find its own handler by id/ when setup runs again: =on/add=
    now reaches the advice. The prototype does, by name in its table.
  - /Advice sits in the middle/: it sees and changes other callers' calls,
    alice's clicks too, and the original then writes with its own rights. Who
    may place into =@60/on= is a =protect= rule on =place= or =move= at that
    node, which Emacs has no equal of.
  - A call made inside a round is queued and returns nothing (SCHEDULER, The
    reference scheduler), so =:filter-return= on a handler's result means
    something only to a caller outside a round.
- Change ::
  - *=next= in a handler call* (process API). The handler's first argument
    gets =next(...args)= when the call came through a slot with a handler
    behind this one; it calls that member, as the same caller. CLOS's
    =call-next-method=; about ten lines in =call=. *Deathly for handler
    advice under the proposal*: without it only =:override= works. Not the
    graph, not =protect=.
  - *The world function goes through its slot* (process API): what
    =handler()= returns calls the first member of the slot its node is in,
    not the node. Then a UI click is advised as a script's call is: a UI is
    an API all the way. A choice, not a need: a walk per click, and a held
    function changes meaning.

* 2. Advising a program's code

*=:override=: yes, by placement.* Spec (Code is a read): a nearer
=programs/p=, or one at position 0 of the same slot, is what the next run
finds. TS, ran: a running process keeps the program it started with and
shows an item saying a nearer one is there; the next start runs it.

#+begin_src ts
api.place({ address: ["a"], name: "programs", id: "a.programs", value: null })
api.place({ address: ["a", "programs"], name: "p", id: "a.p", value: { kind: "b", compute: "nearer" } })
// running in /a:     [{"newer":{"program":{"node":"a.p","time":10}}}, "orig"]
// started after it:  ["nearer"]
#+end_src

*For one process* (the proposal; the prototype, ran): a node in front of the
process's own =program= part. Its setup takes the original, the member
behind, and calls it with a context filtered, so every handler, scope and
effect the program makes is advised. Placing it ran setup with the advice;
unplacing it ran the original again, clean.

  return setup({ ...ctx, handler: (name, f) =>
    ctx.handler(name, (x) => { log.push("around " + name); return f(x) }) })

*=:around= across kinds: a host loader.* Running the original's code takes a
loader, and a program cannot load. The prototype cheats with =new Function=.
One host loader composes two programs, with no core change:

#+begin_src ts

- Cost :: two programs loaded per run; loaders cache by code.
- Awkward :: in front of =/programs/editor= it advises every process that
  finds it. The around program must take the original as the member behind,
  never by the same path, which finds itself. An effect's =api= only writes,
  so it reads the original through =p.reads=, untracked. In TS advice reaches
  a running process only when it starts again.
- Describe :: a record's program entry lists every id in the slot
  (=ProgramEntry.slot=), and TS's =newer= item names a nearer program:
  =describe-function= for code is there already.
- Change :: none in the core; the around loader is the host's. TS is behind
  SCHEDULER's Code is a read.

Three ways, by how the value is read.

moves in front of =@41/home/sum=; it reads the slot and returns f of the

Processes; the proposal, Reading and writing). The prototype writes a scope's

its own node stayed where it was:

// count reads: [["@2.home/count10", 2], ["@1.home/count", 1]]     wanted: [20, 2]

Writes act on the first member that is here (GRAPH, Paths), so a node in

A process's value today: a second process started under the same name goes

=move=, and starts a process that a node covers paused: not yet.

*b. A shadow, for readers by lookup.* Works today. Start the filter nearer,
under the same name; it reads what it shadows:

It reads the one it shadows by path, never itself, so its own writes never
mark it.

*c. A loader, for every reader* (ran, §4): wrap a compute's return. ="orig"=
became ="ORIG"= under =/a= and stayed ="orig"= outside. The original value is
then nowhere but in records.

- Cost :: (a) reads its own slot, so its own value write marks it: one more
  run per change, ended by an equal value. The prototype passes over a
  reader's own changes.
- Awkward :: the owner's own reads by path see the filtered value too, as in
  Emacs, where a package's own calls are advised. =:filter-args= on a scope is
  the same move one level down: its data is its =data= child (the proposal),
  and a node in front of it is the argument it gets.
- Change :: none. The prototype should write values at their ids, as the
  spec does. TS's =Interface= has no =lookups=.

* 5. Advising a graph operation: around every write under =/docs=

| combinator                         | today                                                                         |
|------------------------------------+-------------------------------------------------------------------------------|
| =:before-while= (a veto)           | =enter=: =protect='s =may=, its rules in nodes; a rule placed advises         |
| =:after=                           | =subscribe= to a node; for a subtree, a process that reads it                 |
| =:override= of writes              | a node in front, which takes the writes: an overlay                           |
| =:around=, =:filter-*=             | a wrapper, which only the host builds, once                                   |
| fix it after                       | an effect writing a second change whose cause names the first: both are shown |

#+begin_src ts
function advised(below: Interface, under: string[], f: (op: WriteOp) => WriteOp): Interface {
  const inside = (op: WriteOp) => under.every((n, i) => names(op)[i] === n)   // place + address, as names
  const w: Interface = { ...below, write: (op) => below.write(inside(op) ? f(op) : op) }
  w.top = told(below.top(w))
  return w
}
#+end_src

- Cost :: every operation pays.
- Awkward :: a wrapper learns which node an operation acts on only from its
  =enter=, asked during the operation, too late to change it. Before, it has
  only names, and a node mounted at two paths is advised at one. The stack is
  told its top once, so no program adds a wrapper.
- Change :: a program-added, synchronous =:around= on graph operations would
  need the stack as changeable data (the proposal's question 7) or next.org's
  "ephemeral filter on write and read". Not a deathly wish, and better not: a
  filter inside a change makes its patches differ from what its writer sent,
  with no change saying why. The effect writing a second change says why.

* 6. Removing, ordering, seeing

*Remove*: =unplace({ address, name, id })=. Advice moved in as an ephemeral
node lives as long as both: its advisor's death releases it (SCHEDULER,
Ephemeral nodes), the advised's takes it with its node. Ordinary advice, a
program or a rule node placed by hand, is saved with the graph, like advice
in =init.el=; a handler's advice lasts only while its advisor runs.

*Order*: position. Emacs's depth, -100 outermost to 100, newest first among
equals, is a library: each advice node's value says its depth; the owner's
says none and stays innermost.

#+begin_src ts
// moves the advice node id from its own slot (from, name) into the advised slot (at, name)
function advise(api, from: Address, at: Address, name: string, id: Id, depth = 0) {
  const there = api.read({ address: [...at, name] }).filter((i) => "value" in i)
  const k = there.findIndex((i) => (i.value?.depth ?? Infinity) >= depth)
  api.move({ address: from, name, id, to: at, toname: name, position: k < 0 ? there.length : k })
}
#+end_src

What is missing: /who put each member there, and why/. A slot item carries
the slot's last change, which may be about another member (GRAPH, Open, its

* What it comes to

Works today, by spec, and ran where marked:
- =:override= of a handler (proposal; prototype), a program (spec; TS at the
  next start), a value (by lookup; by a node in front where values are
  written at their ids);
- =:around= and the rest on handlers in the prototype, with the original
  mounted under a second name;
- =:around= on a whole program in the prototype, by a node in front of its
  =program= part;
- =:around= on every run of a kind in a subtree, by a loader node (TS);
- =:after= on runs (records) and on writes (=subscribe=, tracking);
- =:before-while= on graph operations (=enter=, rules in nodes);
- removing (=unplace=, or the advisor dying), ordering (position), seeing
  (reads are lists; the chain in each agent; =newer=; =ProgramEntry.slot=).

Needs:
1. =next= in a handler call: process API, about ten lines. Deathly for
   handler advice under the proposal, whose ephemeral handler nodes cannot
   be mounted elsewhere.
2. The world function goes through its slot: process API. Recommended, or UI
   clicks go around all advice.
3. Values written at their ids: already the spec; the prototype is behind,
   and its scopes are then overlays (ran).
4. A header per slot member: graph, already Open. A nicety for describe.
5. An around loader: the host's, no core change.
6. A synchronous filter on graph operations from programs: not needed; argued
   against above.

The graph needs nothing; the scheduler core nothing; =protect= one rule on
placing into another's =on=. TS is behind the spec on =move=, =enter=, Code
is a read, and covered processes, which is why some of the above waits there.

*The finding.* A union slot already is an advice list: the slot is the
function cell, first-wins is the outermost advice, position is depth, the
members behind are the advised function still there, reads are lists is
=describe-function=, and an ephemeral advice node is removed when its advisor
dies, which Emacs cannot do. The same rule that makes it advice, writes act
on the first member, makes it a hijack wherever the owner writes its own part
by path: the prototype's scope values were taken by the node in front. So
"written at its id", already in SCHEDULER for a process's value, is what
separates advice from an overlay, and must hold for everything a scheduler
writes on a program's behalf.
