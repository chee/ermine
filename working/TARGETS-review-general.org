** 3. Host facts held in ordinary nodes go stale after a restore; held in ephemeral nodes, they break C

** 7. Prior art that is described wrongly or inconsistently
- OCI: "The first matching entry wins, in the author's order", then "Teaches: ... the host ranks". The spec does say first match. containerd instead sorts by what the host prefers and uses the author's order only to break ties. A borrows containerd's rule, not the spec's. Say which is meant.
- npm: "advisory unless strict" is true of =engines= but not of =os= and =cpu=. npm enforces those (EBADPLATFORM), and that is how esbuild's per-platform optional packages get skipped. Newer npm, yarn and pnpm also have a =libc= field (glibc or musl), which bears directly on the libc floor case.
- Item 4, "Unknown is passed over, not an error". This is true of unknown alternatives (OCI entries, npm conditions). It is false of unknown needs: WASI imports, Java's =requires= and Android's required features all refuse. B's own text says "an unknown name is not met". This is the old split between must-understand and may-ignore (PNG's critical chunks, X.509's critical extensions). A does not say what an unknown field means.
- Item 3: the evidence that =os.features= "decayed" is weak. It has a narrow use (Windows' win32k). The field that is reserved and empty is the platform's =features=.
- Item 1: three systems for and three against is not "agree".

** 12. Several builds: the paper gives none of the graph consequences of the two layouts
- Section: A, Several builds; Q5.
- Quote: "a list of {target, code} in the program"; Q5: "A list in the program's value; or the program node's slots".
- Problem: GRAPH.tex settles several things here.
  - A write marks every reader of the node's value. With all builds in one value, re-uploading the riscv build marks every process running the aarch64 build.
  - One value has one header. Who supplied which build is lost, though "every value says which change made it" is the core's promise.
  - A host holds the whole value. To reach its own small build, the RP2040 has to hold the 5.7 MB wasm build too, which it cannot.
  - protect sees one node, so every build has the same writers.
  With a node per build, each build has its own header, its own marks and its own protect rules. Combine host ranking with one set of writers and this follows: whoever may write the program can add a build the Pi prefers, and so decide what runs there.

* Questions for the designer

Asked in an order where earlier answers settle later ones.

1. *How far the 10-07 decision reaches* (the files layer needs Deno and macOS). Does "structured, matched by relation" cover only the machine (the peer's aarch64 ELF)? Or do engines go into its "ABI or API version" slot? Or do engines sit beside it in a shape of their own?
2. *One shape or two* (the peer's native ELF beside the clock's "any JS"). Should the machine axis and the engine axis use the same shape, or may each have its own?
3. *Are host facts saved?* (the Pi restored onto another board; a Deno upgrade between runs). Ordinary nodes: saved, can be stale after a restore, can be mounted at several names. Ephemeral nodes: rebuilt at each start, one place each.
4. *Where a host's has lives* (ermineOS's =c= and =deno-js=; a page's same thread and its worker). One per host, or one per loader?
5. *A loader name that will never arrive* (an RP2040, a bundled =sw.js=). Wait, as for any absent node? Refuse at start, naming it? Or treat "not placed" (empty) differently from "placed, not here" (pending)?
6. *Is picking a build a read?* Either its items show the builds passed over and why (then "Reads are lists" answers Q7), or it is a step inside the loader that shows only what it picked.
7. *Where several builds live* (subduction-c's packs, if subduction-c is ever a program). In one value: one header, one set of writers, every host holds every build. Or a node per build: each with its own header and protect rules, and a host may hold only its own.
8. *Who ranks the builds.* The host's order: whoever may add a build can choose what the Pi runs. Or the program's order: an emulated build listed first wins.
9. *An unknown field or need* (a program written for a newer host names a world today's ermineOS lacks). Refuse, pass over, or mark each field as must-understand or may-ignore?
10. *ermine's own interface* (the JS context, steps' ops, PROTOCOL lines). Does a program say which version it was written for? Options: nothing, as today; a version beside the loader name; or read from what the program calls (D).
11. *What "any JS" means* (the clock program). Plain ECMAScript plus ermine's interface; WinterTC's set; or whatever =loaders/js= gives on that host?
12. *Who adds names* (=loaders/js=, =wasi:preview1=, field names). A list in core, a library, or each host?
13. *Who writes the needs* (the peer's glibc floor). A person; a tool that reads the bytes and stores the result as a node (=dpkg-shlibdeps=, =auditwheel=); or no one (D)? If the tool, should the paper add it as an option before Q1?
14. *A subtree that must not run something* (=untrusted/= and native code). Is this needed now, or is a chroot enough?
15. *Building on the host* (C11 from source on the Pi; the laptop building for the Pi). Part of targets, or a separate program whose output is a build?
