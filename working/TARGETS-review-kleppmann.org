* Findings

** Shared or local

*** F1. Loader nodes are local names stored in shared data
- Section: §1 Today (Loader node); §4 C (Host).
- Quote: "a key in the host's own table; an ordinary node"
- The key means something only to the host that placed it. The node holding it is ordinary, so a host saves it (GRAPH, Nodes: =restored= holds "the ordinary nodes"). The paper never says whether =loaders/= syncs.
- If it syncs: a Mac and a browser both place into =loaders/js=. The slot holds both ids, in the same order on both devices once they converge. GRAPH's walk takes the first id whose node is here, and after sync both are here. So one device finds the other's ={"loader": "deno-js"}=. It is here, so it is not pending. Its key is unknown, so the result is =no-loader=. The device's own loader, later in the slot, is never tried.
- If it does not sync, the paper does not say where host-local nodes sit in a tree that otherwise syncs.
- Same for A's =/host/target= and B's =/host/has=: each is one fixed path, and every device writes it. Two devices writing it concurrently leave one device reading the other's facts as its own.

*** F2. "The host, by placing" holds only if no one else can place
- Section: §4 C (Who); §2 Two levels.
- Quote: "Who: the host, by placing; the search, through the view."
- Lookup takes the nearest match. Anyone who can place into a folder above a program picks that program's loader on every device. That includes a peer editing a shared folder.
- Case from the paper: =untrusted/js= is answered with =worker=. A peer places a nearer =loaders/js= saying =same-thread= inside a shared folder under =untrusted/=. The programs there leave the worker on my device.
- The placement's header names the peer's agent, but the search does not look at it. "met by where the host places the loader" (§2) has the same gap. The paper does not say whether it relies on =protect= here.

*** F3. A match has four inputs; the paper names two
- Section: §4 Options (intro); Through every case.
- Quote: "how does a program say what it needs to run; how does a host say what it has; how do the two meet?"
- On device X, a match reads four things:
  - the program, as synced so far, which may be older than an edit made elsewhere;
  - the loader nodes it can reach, some perhaps a peer's (F1);
  - the host facts, as last written;
  - the matcher's own code, "a library function" that ships with the app, so each device may run a different version.
- Only the first two are graph data with headers. Host facts are graph data only under A and B. The matcher's version is recorded nowhere.
- So two devices holding the same synced graph can match differently, and nothing shows why. Q7 asks whether skipped builds can be read on one device. It does not say whose record that is if the record syncs.

*** F4. Which build ran is invisible to anyone reading its output
- Section: §3 (a JS part and a native part; better with, runs without); §4 (Several builds, every option).
- Quote: "the files layer on Linux (no xattrs, no swap)"
- The =files= layer takes a libSystem path on macOS and the Linux path elsewhere, and Windows takes the Linux path. Two devices run "the same program", one with xattrs and one without, and both write into the synced graph.
- A change's header has agent, process ("to the graph, only an id"), site, cause and time (GRAPH, Changes). It has no build and no target. A reader cannot tell a value came from the weaker path.
- The table grades D "works best: the code probes". Probe results are written nowhere. The paper notes that "Reads are only ever recorded" is about graph reads. It does not draw the conclusion: probes of the machine are neither declared nor recorded, so two devices diverge with no trace.

** Naming without an authority

*** F5. No one mints the names, and the paper spells one thing several ways
- Section: §4 A, B, C (examples); B (Where it strains).
- Quote: "the names need a vocabulary, and an unknown name is not met"
- One WASI world appears as =wasi_snapshot_preview1= (A), =wasm32-wasip1= (A, as a triple), =wasi:preview1= (B) and =wasi-p1= (C). macOS appears as =macos= (A), =os:macos= (B) and =darwin= (C, and =Deno.build.os=).
- Under B or C, a program written with one spelling never matches a host that lists another. That holds on every device, and the only error is "missing".
- §3 says of triples "one machine has three spellings" and "a string is a poor identity". The options then repeat the problem.
- B has ermine define "any JS, steps". Nothing says who mints =deno:ffi=, =libssl.3= or =isa:aarch64=. A matches "equal after aliases (=arm64= is =aarch64=)", but nothing says whose alias table that is. Two devices with different tables disagree about the same program on the same facts.
- One name can also mean two things:
  - =loaders/js= is any JS on one host and Deno with every flag on another. Q2 faces this on one host only.
  - =deno=, =node= and =steps= carry no version, although B's own rule is "the version is cut into the name". Deno 1 and Deno 2 differ in which =Deno.*= calls exist.

** A program on a device that cannot run it

*** F6. "No match" cannot tell "not yet" from "never"
- Section: §4 C (No match); Q6.
- Quote: "pending, as today; the loader may yet arrive"
- With no central authority, a device cannot know whether any peer will ever place =loaders/deno-darwin=.
- Pending is honest about "not yet". On a browser, an RP2040 or a bundled =sw.js=, it means "never", shown forever as "not yet". A person sees a program that looks as if it is loading.
- A and B refuse instead. That is honest about "now", but stays wrong after a device is plugged in or a permission is granted, unless something re-matches (F7).
- Q6 asks pending or fail. It does not ask whether a host can say its set of loaders is closed. The fixed tables (§2) know that; other hosts do not.

*** F7. Nothing re-matches unless a host writes a change
- Section: §3 (a target that changes); the walk-through row of the same name; Q10.
- Quote: "works: placement is a read"
- GRAPH marks readers only when a node changes (Tracking). A revoked permission, a plugged-in device, a glibc upgrade or a Deno upgrade changes no node until host code writes one.
- Under every option, then, re-matching needs a duty the paper never states: the host watches the machine and writes each fact that changes.
- Some changes a host cannot see at all, such as a library removed under a running process.
- D's "live facts, no stale node" also means no change and no mark. It is right once, at start.

*** F8. Host facts go stale after a restore and across a link
- Section: §4 A (Where it strains); §3 (on another device).
- Quote: "written at start, it goes stale (a glibc upgrade)"
- After a restore: a host saves an ordinary target node or loader node and restores it (GRAPH, Nodes). After an OS upgrade, or once Deno is gone, the restored node states the old facts until the host rewrites it. A scheduler that matches before then uses them. An ephemeral node is never saved, so it is absent (pending) until written, which is safe but empty. The paper does not say which kind host facts are. Today's loader nodes are ordinary.
- Across a link: the laptop reads =/pi/@41= to build for the Pi. During a partition it reads the last copy it has. GRAPH's time names a change "in a graph", so the laptop cannot compare it with its own clock. It cannot tell "the Pi is unchanged" from "the Pi's update has not reached me". PI-OS's target is "at no named path".

*** F9. Programs reach devices that cannot hold them
- Section: §3 (RP2040); §4 A (Several builds); Q5.
- Quote: "264 KB of RAM beside a 5.7 MB module"
- A node that is here has its whole value (GRAPH, Values). A keeps its builds in the program's value. So every device that holds the program holds every build: the RP2040 holds the 5.7 MB wasm and the Mac's Mach-O, only to learn it can run neither.
- The paper treats size as a need to be matched. It is first a question of which devices receive which builds. Q5 (a list or a folder per target) bears on this but is not argued from it.

*** F10. Who starts a synced program is assumed, not said
- Section: §3 (on another device); §4 (No match, in each option).
- Quote: "placed there, started by a process there"
- Each option's "no match" means something different in two cases. If a synced program starts on every device that has it, every unlike device shows a refusal or an endless pending. If it starts only where a person starts it, only that device does.
- Whether placing starts anything is open in the scheduler. The walk-through grades every case without saying which case it assumed.

** Concurrency

*** F11. Several builds of one program may come from different sources
- Section: §3 (one program, several builds); §2 Builds-for; §4 A, B, C (Several builds).
- Quote: "a list of ={target, code}= in the program"
- Every table of builds in §3 is one artifact, built in one place and then fixed: an OCI index, a fat binary, subduction-c's packs.
- Here, builds are values any device can edit. The Pi builds its own (C11, =util.h=) while the Mac rebuilds after an edit. Nothing ties a build to the source it came from. The list can hold a Mac build of today's source beside a Pi build of last week's, and each device runs a different version unseen (F4).
- None of A–D records a build's source.

*** F12. Needs and code can be edited apart; under D they cannot
- Section: §4 A, B, C against D.
- Quote: "={"needs": ["deno", "deno:ffi", "os:macos"], "code": <c>}="
- In A, B and C the need sits beside the code, under another key. Two devices edit at once: one narrows =loader= to =loaders/deno-darwin= for FFI, the other makes the code portable. If keys merge separately (SYNC.tex's rules, not read here), the result is portable code pinned to Mac Deno, a pair no one wrote.
- D reads needs from the bytes, so they cannot drift from the code. The walk-through never credits D with this. §3 notes "claims drift from it" only for a single author.

** Definitions

*** F13. Host, target and has are never defined
- Section: §1; §4 A.
- Quote: "One node per host, while a host's has differs per loader"
- "Host" is used for a device (the Pi), a runtime (Deno), the holder of a graph (the service worker, "its own graph"), and per loader ("a has per loader"). A match "per host" means a different thing in each.
- "Target" names both the need (="target": {"libc": ">=2.36"}=) and what a host has (=/host/target=, ="libc": "2.36"=). One side takes ranges and "any", the other single values.
- "OS and a version range" does not say kernel or userland. The 32-bit Pi row shows the two differ, and A's example carries both =version= and =libc=.

*** F14. The need record has no rule for fields it does not know
- Section: §4 A (Program); B (Where it strains).
- Quote: "A missing field is any."
- The paper says nothing of an unknown field. Suppose a newer device adds one, such as RAM for the RP2040 row. An older device's matcher either ignores it, and the program runs and fails at first use, or refuses it, and refuses programs it could run.
- B is the same: a name ermine adds later is "not met" on older devices.
- Devices that sync run different versions, and nothing says which way they fail.

** Claims and prior art

*** F15. "None covers both axes" is false
- Section: §3 What they agree on, 8.
- Quote: "None covers both axes."
- Python wheel tags (PEP 425; manylinux, PEP 600) carry an interpreter tag, an ABI tag (=cp312=, =abi3=) and a platform tag with a glibc floor (=manylinux_2_28_aarch64=). The installer computes the ordered list of tags its interpreter and machine support, best first, and takes the best wheel.
- conda's virtual packages (=__glibc=, =__osx=, =__cuda=) put host facts into the same solver as packages, with version ranges.
- Both cover engine and machine, and both treat levels as names that the host expands (B's "a host at x86-64 v3 lists v2 too"), at large scale. Neither appears in §3.

*** F16. Matching done by a store is read as a host's check
- Section: §3 (Java modules, Android and iOS); (Deno's lib, JSR).
- Quote: "Android: =uses-feature= with =required= true or false"
- Google Play uses =uses-feature= to filter which devices are offered an app. Android's own docs say the system does not check it at install, so a sideloaded app installs anyway.
- The App Store uses iOS's =UIRequiredDeviceCapabilities=. I did not confirm whether the device also checks it.
- JSR's "works with" lives in the registry.
- All three rest on a central store with a list of devices. ermine has none, so they do not support "refuse early" for a host acting alone.

*** F17. npm: os and cpu are enforced, and esbuild's scheme is a known failure of exactly this kind
- Section: §3 (=engines=, =os=, =cpu=, =devEngines=).
- Quote: "advisory unless strict"
- Only =engines= is advisory unless =engine-strict= is set. =os= and =cpu= refuse the install (=EBADPLATFORM=), and an optional dependency that fails them is skipped quietly. esbuild's per-platform packages rely on that skip.
- The skip gets written into =package-lock.json=. A lockfile made on one OS has been known to lack the other OS's optional package, so a clone on another OS installs cleanly and fails at run. That is npm/cli issue 4828, which rollup's error message cites.
- That is this paper's own question: a match made on one device, synced as data to an unlike one, in a real system. The paper reads esbuild only as "native first and portable last". By contrast, Python's =pylock.toml= (PEP 751) keeps an entry for every wheel and leaves the pick to the installer.

*** F18. OCI: the author's order or the host's?
- Section: §3 OCI image index; §4 A (Several builds).
- Quote: "The first matching entry wins, in the author's order; a runtime expands what it can run into a best-first list"
- The spec says a client SHOULD use the first matching entry. containerd sorts the matching entries by its own platform order and uses the author's order only to break ties (worth checking against its source). A copies the second ("the host's order ranks them, the program's breaks ties").
- The paragraph states both rules without saying which one runtimes follow.

*** F19. Agreement 4 overstates
- Section: §3 What they agree on, 4.
- Quote: "no match is a refusal that names what is missing"
- Java and WASI name the missing module or import.
- Docker says "no matching manifest for linux/arm64/v8", which names the host, not what each entry lacked.
- Node's =ERR_PACKAGE_PATH_NOT_EXPORTED= names the subpath, not the conditions it tried.
- npm's optional skip names nothing (F17).

*** F20. "A browser update takes effect on reload"
- Section: §3 (a target that changes).
- A browser update applies when the browser relaunches. Until then, a reload gets the old engine.
- A new =sw.js= waits for the old pages to close, unless it calls =skipWaiting= and =clients.claim=. In that case the old pages get the new table mid-life: two versions under one name, on one device, at once.

*** F21. A pass before start is a guess, but the grades call it "works"
- Section: Through every case (wasm; RP2040, D).
- Quote: "works for wasm: size read before start"
- A wasm module's memory minimum is only a floor. =memory.grow= can still fail, and the byte length does not say what an interpreter needs in order to hold the module.
- A check before start can refuse soundly. A pass means only "not refused yet". The paper notes trapping shims, but the grades still treat a pass as "works".

*** F22. It leans on unread papers for what it needs, and never cites sync
- Section: §1 Today; §4 C (Meet); §4 (intro).
- Quote: "found as a program is, by =LOADERS.tex='s search, each step of which reads the whole path"
- Every option rests on one step: which loader node a name resolves to. That step is defined in =LOADERS.tex=, not here or in GRAPH. Whether it gives the same answer on two devices with the same synced tree (F1, F2) cannot be checked from this paper.
- More claims rest on other papers:
  - "None changes =SCHEDULER.tex=" rests on =code(process, view)=.
  - Pending versus =no-loader= comes from =LOADERS.tex=.
  - "Silent drop" comes from =build.org=.
- The paper's cases are about programs reaching unlike devices, yet it never cites =SYNC.tex=. "sync" appears once, as a harness name (=browser-sync=), and "over a link" is its only phrase about more than one device.

* Questions for the designer

These sit beside TARGETS' own Q1–Q12 and do not repeat them.

1. *Host facts and loader nodes: synced, saved, or neither?* Case: a Mac and a browser both place into =loaders/js= (F1); a target restored after an OS upgrade (F8).
   - ordinary and synced, as any node;
   - ordinary and kept on this device: saved and restored, never sent (where in the tree?);
   - ephemeral: never saved and never sent, rewritten at each start. C's one node in three slots would then be three nodes.
2. *A loader node whose key this host lacks.* Case: the browser finds the Mac's ={"loader": "deno-js"}= first in =loaders/js= (F1).
   - =no-loader=, shown;
   - passed over, as a node not here is.
3. *Who may choose the loader for a program on my device?* Case: =untrusted/js= is answered with =worker=, and a peer places a nearer =loaders/js= saying =same-thread= (F2).
   - anyone who may place there, so it is =protect='s call;
   - only placements made by this device's host count;
   - only loader nodes outside synced folders count.
4. *Who mints names?* Case: =wasi_snapshot_preview1= / =wasi:preview1= / =wasi-p1=, and =macos= / =os:macos= / =darwin= (F5).
   - one list in =core/=, and an unlisted name is refused;
   - outside registers, spelled as they spell them (WASI, LLVM triples, =Deno.build.os=);
   - anyone mints names, and each host keeps its own aliases, which may differ.
5. *A field or name from a newer device.* Case: a RAM field added for the RP2040, read by an older device (F14).
   - ignored;
   - refused;
   - each field marked "may ignore" or "must know", as X.509 marks its extensions critical.
6. *Builds and their source.* Case: the Mac's build of today's source beside the Pi's own build of last week's (F11).
   - nothing recorded, as today;
   - each build names its source, and a mismatch is shown;
   - a build of an older source is skipped.
7. *Which build ran, and by which matcher: who can see it?* Case: the =files= layer's macOS path and Linux path, writing into one synced tree (F3, F4).
   - no one;
   - the device that ran it (a local record);
   - every reader of the changes it made.
8. *Does the RP2040 receive the 5.7 MB build?* (beside Q5) Case: F9.
   - yes: every device holding the program holds every build;
   - no: a device fetches only the build it picked.
9. *Can a host say a loader will never be here?* (beside Q6) Case: an RP2040 or a bundled =sw.js=, against a browser that may yet get a loader (F6).
   - no: a missing loader is always pending;
   - a fixed host says its table is closed, and a miss there is refused;
   - any host may say, per name, "never here".
10. *Who writes a host fact when it changes?* (beside Q10) Case: a revoked Deno permission, a plugged-in device, a glibc upgrade (F7).
    - the host writes a node for each change it can see;
    - facts are read only at start, and a change needs a restart;
    - each fact is one or the other, as listed.
11. *Which does this paper's walk-through assume?* Case: a synced program reaching a device that cannot run it (F10).
    - it starts wherever it is placed;
    - it starts only where someone starts it;
    - both, graded separately.
