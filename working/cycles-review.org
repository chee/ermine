A reviewer's answer to: "would things overall get simpler or more complex if
we banned cycles? ... lay them all out in a table". SCHEDULER.tex was read

* Short answer
Banning cycles everywhere would make ermine more complex. Most places can't
form a cycle anyway (by construction, or because walks follow routes); the
places that do loop either want loops or already handle them. One ban pays:
no cycle made only of ordinary nodes' slots, and only if a node goes when
its last slot lets it go. With free(id) or a sweep, there is nothing to ban.

* Letting go, each way
- Refuse ordinary-only cycles: the holder count is exact and local, as in
  Unix. The price is mutual links as slots.
- Sweep from the root: always exact, covers the whole graph; could run when
  idle, or reuse the files store's root-down pass.
- Mark a slot that holds an ancestor and don't count it: wrong in a DAG.
  Root holds A and C; A/y mounts C; then C/x mounts A. If "ancestor" means
  reachable, C/x is marked; unplace root/a and A goes though root→C→x still
  reaches it. If it means on the route at mount time, nothing is marked;
  unplace root/a and root/c and A and C hold each other forever. Getting it
  right needs a reachability check when a count hits 0, which is a sweep.
- free(id): cycles don't matter; slots still holding a freed id read pending.

Whichever way: ids kept outside slots (references, a run's {node, time},
cache leaves) can come to name a gone node, so "placing its id again brings
it back as it was" (GRAPH.tex:127-128) stops being true.

* Twin-width
Banning cycles doesn't get it: any graph is the shape of some DAG. What
decides it is the pattern of sharing. For this decision it doesn't matter.
The separate twin-width review (10-09) says drop it: mounting builds every
graph; every rule that bounds it bounds sharing; ermine's questions are index
lookups (holders, readers in graph.ts) or reachability.
