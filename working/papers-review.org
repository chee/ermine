#+title: Papers review: implementable, small, explainable

Five reviewers read every paper for implementability, scope creep, LLM
crimes, smallness, and whether a person can keep it in their head. Items
already queued in next.org were left out. Nothing was edited.

* What runs through all of them
- A builder learns the rules from the scenarios and the other
  implementations, not from the papers. The OCaml and Zig graph builders
  said so (core/graph/*/FEEDBACK.md). Graph can be built with the
  scenarios open beside the paper. Protect is only half that way, because
  the paper and the code disagree. The scheduler can't be built from the
  papers: about 35 scenarios contradict them, and nothing marks which.
- Rules live only in PROTOCOL, a HARNESS.md, or the code, while the paper
  that owns them says nothing. Examples: above-root, exists, the order of
  marked and of directory, runs counting from 1, handler replacement.
- Rules appear in two to five places. The worst: the stack order (4 times
  across HOST and ARCHITECTURE), `schedule(protect(graph()))` (3 papers),
  the Plan 9 union (4 times in GRAPH), "show, don't decide" (5 times in
  SYNC), "a lock never signs" and "ids are not secret" (both SYNC and
  LOCK).
- Proposals are written as decided, or something is both decided and
  Open. Examples: SCHEDULER's folder and pid format; SYNC storing lock
  messages, rebase, and the records document; LOCK's three answers for
  member; KEYHIVE's "shown"; CACHE's "programs opt in".
- Stale or false claims:
  - SYNC's abstract says "nothing built" (sync.ts is 2567 lines and sync.c
    2762).
  - SYNC's C section describes a websocket thread.
  - KEYHIVE's C crate would have to be std.
  - HOST and ARCHITECTURE say "only mirrors are built" (LINK is built).
  - ARCHITECTURE draws the cache as an idea.
  - PROTOCOL: "a scenario checks that through $eq", which none does.
- Claims about other systems that were never checked:
  - Plan 9's ls (it concatenates; ermine groups by name);
  - DAG-JSON escaping (it has none for "/" keyed maps);
  - Node's resolve hook (it is about where);
  - Smalltalk methods taking effect at once (not for frames on the stack);
  - Subduction's "lower blob digest" (it is the whole commit's digest);
  - keyhive.rs line numbers (wrong for 0.6.0).
- Citations stand in for reasons: Solid is cited 19 times in SCHEDULER.
- Hedges pile up: SCHEDULER has 9 "proposed", 2 "under review" and 3 "for
  now"; LINK has 20 open markers and 9 default markers.

* Holes that need chee, ranked
Each item gives the case, then the choices. The lean is mine.

1. The lock's `open(doc, name, parents, bytes)` can't be called. A
   receiver learns a change's name and parents only by opening it. TS
   passes `"", []`; C passes the bound id and Subduction's parents (and
   names the doc by the bound id in close too, against LOCK). It works
   today only because "unlocked" and Keyhive ignore those arguments. The
   small lock in LOCK could never open what it sealed.
   - a. `open(doc, bytes)`. Keyhive's EncryptedContent carries its own refs.
     (lean)
   - b. open is given Subduction's stored ids.
2. A covered process writes over the node in front of it. This follows
   from "keeps running underneath": the value write goes through [name],
   and a write acts on the first member. Case: start a clock named clock
   under apps when apps/clock is already a document. Every tick writes the
   time over the document. The same holds for its log and answer nodes.
   - a. The scheduler writes the process's own node, not the address
     (needs something that writes by node).
   - b. While covered, the scheduler writes nothing, and the process's
     items show when it is uncovered. (lean)
   - c. A start under a name that is taken is `exists` (this fixes only the
     start case).
3. SYNC: a change made here on another device's behalf (through the link)
   carries that device's pid, so every receiver refuses it as `device`
   (SYNC l.162–164, and TS does this).
   - a. A pid naming another device is a claim, shown and not refused, as
     LOCK treats any actor claim. (lean)
   - b. The owner re-qualifies it.
   - c. Keep refusing.
4. SCHEDULER: a call from inside a round can't "return once the round is
   done, with its own answer" on one thread. Case: an effect calls
   button.click().
   - a. It returns at once; the handler runs in the next round and its
     answer lands in a node. (lean)
   - b. It runs nested, at once.
   - c. Refused while a round runs.
5. A refused read still marks the reader, and the compute is handed "the
   changes kept for it" whole, patches included. So P sees the patches of
   a node it was refused.
   - a. A refused read's changes come as headers, without patches. (lean)
   - b. A refused read doesn't track (this reverses a decision).
6. SYNC says process nodes are documents, yet "never committed", so what a
   program places under its node waits forever on other devices.
   - a. Process nodes are not documents: processes are local. (lean)
   - b. They are documents, and their value is committed too.
7. Every Keyhive call is async, while LOCK's may must answer at once. On a
   cache miss, one build says no, one says yes, one blocks.
   - a. No until known; changed() then marks the readers, as any change of
     access does. (lean)
   - b. may gains a third answer, wait, and reads show waiting.
8. LINK: two hosts interoperate only by copying wire.ts, since frames,
   numbering, handshake, pieces and bye are all Open (O4), though built
   three times.
   - a. Decide the reference wire as built. (lean)
   - b. Say "copy wire.ts".

* Each paper in 10 lines
** GRAPH
1. A graph is nodes with ids. Each holds a value (JSON-like plus bytes and
   typed arrays; an ephemeral node may hold a live thing) and a directory
   of named slots, each an ordered list of ids.
2. Nodes are made, mounted and shared by placing ids into slots. A node is
   reachable only while a chain of slots from the root holds it. Ids are
   only for placing; everything else goes by path.
3. A path walks names down from an interface's place. In each slot it
   takes the first member that is here and has the next name. `..` goes
   back along the place's walk, and nothing above the place's start can be
   named.
4. Every read returns a list of items: the thing read, its from (the route
   that won), and the header of the change that last set it.
5. Values change only by patches (snapshot, splice, set), all or nothing. A
   change is patches, a placement or an unplacement, with agent, process,
   cause (the site, when made from outside), and a time from an outside
   clock that always increases.
6. lookup(name) reads that name's slot in each directory up the place's
   walk. The nearest slot with a node that is here wins, so configuration
   is placement.
7. A recorded run's reads are kept under its id. A change to any of them
   marks it, and the operation returns what it marked. The graph never
   runs anything.
8. An ephemeral node is in exactly one slot and is never kept. Unplacing it
   lets it and its ephemeral descendants go in that one change, children
   first.
9. Interfaces are bound to an agent, a process and a place. Wrappers
   (protect, a scheduler) stack over the graph and check from the outside
   in.
10. Whoever keeps the graph keeps its ordinary nodes, their last
    non-ephemeral changes, and the highest time.

** SCHEDULER
1. The graph only marks readers; a scheduler runs them, and every scheduler
   shows a marked process that hasn't run yet as waiting.
2. start(address, program) makes a node under a new pid and runs it there.
   Only start starts anything, and a process lives in one slot on one
   device.
3. Each run searches up from its place for the program, then for
   loaders/<kind>, as tracked reads. New code means a new runnable;
   finding nothing means pending.
4. A program is a compute (reads; returns a value or pending) and an
   optional effect (writes; gets a lasting interface and handlers; returns
   a cleanup).
5. The compute's value is written to the process node when it changes or
   settles. Reading a process gives waiting, stopped and error items in
   front of that value.
6. A round runs due computes lowest height first (then oldest mark, then
   id), then each process's cleanup and effect once. What effects mark
   waits for the next round.
7. Every change that marked a process is handed to its runs until a run
   reaches its effect.
8. A request may cause at most a budget of runs; work that arrives
   mid-round is queued.
9. Unplacing the node, or anything above it, kills the process; stop ends
   it in place. Either way, children end first, the cleanup runs,
   ephemeral nodes are released, and the graph forgets it.
10. Every change carries an agent listing the chain of processes behind it.
    Its last step names the run, handler, cleanup, item write or kill.

** LOADERS
1. A loader is host code that turns one kind of program into a runnable: a
   stop(why), plus the program's parts as functions.
2. The host hands schedule its loaders by name. A loader node {"loader":
   name}, found by searching up for loaders/<kind>, says which one a
   subtree uses.
3. With no loader node the run waits. A name the host lacks fails, as
   no-loader.
4. Changing or shadowing the loader node restarts the code under the new
   loader.
5. Parts are called synchronously and return a value, pending, or a
   cleanup, or they throw.
6. Everything the code does in the graph goes through interfaces bound as
   the process.
7. Every start ends with exactly one ended(why).
8. A runnable with no parts is a client that acts on its own.
9. Code elsewhere answers like slow work: pending, then an answer under the
   process node, which the next run reads.
10. A closure (a live function in an ephemeral node) is a program that
    needs no loader.

** PROTECT
1. protect asks the host's may(agent, process, op, args) before every read,
   directory, lookup, write, place, unplace, subscribe and unsubscribe. A
   no refuses with a why, before the graph looks.
2. Nothing else is asked (bind, record, finish, release, apply, batch,
   start), only the operations made inside them.
3. `node` is what the address reaches: the parent for place and unplace,
   the current node for unsubscribe, none for lookup. `id` is the id
   placed or unplaced.
4. Each directory an address's walk reads is asked as a directory read.
   The place's own walk is not asked.
5. A refused union member is passed over, and its position is listed in
   the route. If every member was passed over and any was refused, the
   operation is refused.
6. Members a read hands over after the first are asked one by one; a
   refused one shows as a refused item in its place.
7. A refused lookup step ends the search with a refused item.
8. A subscription is asked again when it reaches another node. Nothing is
   sent while it is refused.
9. Rules are a list where the first full match wins and no match allows.
   Their fields are agent, peer, person, trusted, process, program, op,
   node and id.
10. A run's program and loader searches are the process's reads, so
    whoever can write where a process searches chooses its code.

** PROTOCOL
1. A harness reads one JSON request per line and writes one answer per line
   with the same seq: ok, error or unsupported.
2. Values are JSON, with {"/": …} for bytes, typed arrays, live values,
   non-finite numbers and "/"-keyed maps. An absent field is left out,
   never null.
3. reset builds graph, protect(rules) or schedule(protect(graph)) on a
   root. Below schedule, changes carry time; with it, its clock numbers
   them.
4. Requests carry agent, and may carry process, place and chroot to act as
   that.
5. Commands are the graph's operations, plus start, stop, batch, fire,
   subscribe/events and reload. Reads answer item lists. Changes answer
   {change, marked, gone, runs, stopped}.
6. Items, froms, routes, changes and records have fixed shapes.
7. Errors are {kind, op?, why: {code, …}} from a fixed table, checked in
   the order request, interface, protect, graph.
8. Programs are data: {kind: "steps", compute, effect}, run by the
   harness's one loader.
9. A pid is a fixed function of its start's time, so scenarios can predict
   it.
10. A scenario is a list of {send, expect}. Expected maps match as subsets,
    and $capture binds values that can't be known ahead.

** SYNC
1. One Ed25519 key per device is its Subduction peer id and the signer of
   every change it commits.
2. Every node that is not ephemeral is a document: one sedimentree and one
   lock. Its id is BLAKE3("ermine/v0/id", lock name, make id), so its lock
   is fixed.
3. A change made through the sync wrapper becomes a deterministic CBOR
   blob, named by its BLAKE3.
4. The blob is signed over "ermine/v0/change" and the name, closed by the
   lock, and stored under the seal's hash.
5. The sync process opens and checks every commit of the documents it
   follows, then applies it through arrive. It lists what is refused,
   waiting and stuck.
6. A value and each slot are chains. Concurrent heads read as one item per
   side, ordered by Lamport then name, and a write settles the heads it
   names.
7. A slot's shared members are an RGA list. Every position of a concurrent
   move is shown.
8. Making a node is two commits, the placement and the child's first write.
   A mount reads as pending until that write arrives.
9. Ephemeral nodes travel as Subduction ephemeral messages, with sessions,
   seq, want and beat.
10. A revoked signer's changes are kept and shown. Names, times, refusals,
    chains and sides are kept beside the graph.

** LOCK
1. A lock decides who may relay, read, edit or administer a document, and
   seals its changes. Sync calls it and protect asks it.
2. It has a name, bound into document ids. Its calls name a document by its
   make id.
3. Authorization: may (yes or no), member (yes, no or wait), cut, changed.
4. Encryption: make(parent?), answered at once, offline, or as can't;
   close; open, which may wait or refuse.
5. Shared: outbox, take, state.
6. An actor {"<lock>": k} passes if the signer is k or a member of k.
   Any other actor is an unchecked claim.
7. protect's may: a read needs read and a change needs edit, asked of the
   node's document with the agent's key.
8. "unlocked" seals nothing, always says yes, and has no cut, messages or
   state.

** KEYHIVE
1. The device key is its Keyhive individual. Keyhive's state is saved with
   it.
2. may is best_access_for_doc. member is reachable_members. Both are cached
   and dropped when membership changes.
3. make takes a ready document and group from a pool made offline. A
   parent's group becomes Admin of the new one, and an empty pool refuses
   the placement.
4. Each node has its own group, as Admin of its document. Groups are
   nested, so the trees stay in step.
5. close and open are try_encrypt/decrypt_content, with the name as the
   content ref and the parents' names as predecessors, written as bincode.
6. Events travel as lock messages in sync's tree. Subduction's Keyhive
   frames and policies are not used.
7. member waits on a group it doesn't know.
8. Revocation affects only future keys, and nothing is re-encrypted.
   Revoked writers' changes read revoked: true.
9. C links Keyhive through Rust, in a std crate.

** LINK
1. One host owns a subtree and serves it. Mounters send it PROTOCOL lines,
   applied at the owner's time. There is one writer and nothing merges.
2. A channel carries signed payloads, best effort and in any order. A word
   hashes to a channel.
3. A mounter's request acts at the served node as its /, is stamped
   {actor: claimed, peer: verified key}, and never acts as a process.
4. A mounter may read, directory, lookup, write, place, unplace, subscribe
   and unsubscribe; events are pushed.
5. Numbers cross unchanged.
6. The mounter is shown the owner's key, and the host decides whether to
   accept it. A quiet mount redials.
7. The reference wire: numbered JSON frames, pieces, hello/serve, beats,
   gap, bye.
8. When a link ends, pending requests fail with gone and subscriptions end.
9. A relay serves a program that speaks lines, and coalesces snapshots.
10. A share is a process, and the share guard refuses ids from outside.

** CACHE
1. The cache is a loader that wraps another. It caches a compute's value,
   never an effect.
2. A compute's reads are steps, and its runs form a tree whose branches are
   answer hashes and whose leaves hold a value and its run.
3. Keys are BLAKE3 over canonical CBOR, chained from a root key the host
   gives. Code with no key isn't cached.
4. Replay makes each step through the run's own interface. A leaf is a
   hit; a miss runs the code with the replayed answers.
5. A hit is a run: the same reads, marks and value, and the record says it
   came from the cache.
6. Answers hash by value until some run looks at from or change, then
   whole for good. Errors hash by kind and code.
7. self, name, cwd and changes become steps at first use.
8. Never stored: effects, pending, thrown errors, live values, diverged
   runs, code with no key.
9. A run that diverges shows an untracked read.
10. Losing entries costs runs, never values.

** HOST and ARCHITECTURE, as one
1. The core is the graph. The reference scheduler and protect are wrappers
   a host may replace.
2. A wrapper returns the interface it was given, so they stack: graph,
   keep, observer, protect, schedule, sync.
3. Everything else is a layer: keep, cache, link, sync, locks, loaders,
   libraries.
4. A host makes the graph, builds the stack, holds the bare graph, and is
   trusted.
5. It gives the root, clock, loaders, rules, boot image, sites, person and
   live things.
6. A change enters at the top, gets a site, a time and an access check, is
   applied, goes to subscribers and marks processes.
7. A restart keeps ordinary nodes and the highest time; process nodes come
   back stopped.
8. Link: one owner, nothing merges. Sync: each device has its own graph,
   and histories merge.
9. Each part is a folder with its paper and one subfolder per language;
   conformance/ runs every harness.
10. The papers table says which paper holds which rules.
