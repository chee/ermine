* Findings

** Matching: a check, or a search

*** F1. Every option matches one program alone, but the paper's own cases tie choices together
- Where: §2 Cases (Patchwork tools; a JS part and a native part; Deno).
- Quote: "two copies share no documents"; "so must match it (Debian's same)";
  "its flags are set once for all".
- One program choosing one build from a list is a filter followed by an order.
  That is a check, and its cost grows only with the number of builds. It
  becomes a search when one choice limits another:
  - tools on one page must share one Automerge (pub's rule of one version per
    package per app has this shape; so do npm's peerDependencies);
  - a =.node= addon build must match the ABI of whichever JS loader the same
    program ends up with;
  - every program in ermineOS's one =deno-js= shares one set of flags.
- None of A–D can say "the one X uses". The walk marks Patchwork "awkward" in
  all four columns without saying why: it is not a question about one program.
  The paper never says whether matching is done per program or across the
  programs placed together. That choice decides whether ermine needs a solver.

*** F2. The paper doesn't name what makes matching hard
- Where: §4.1 A, Meet; §4.2 B, Several builds.
- Quote: "the host's version in the range"; "alternatives ... in the program's order".
- Search is hard when there are alternatives, ranges with upper bounds, and
  choices tied together. Deciding whether such a set can be installed is
  NP-complete (shown for Debian packages in 2006). That is why apt, pub and Cargo
  carry real solvers. Go's minimal version selection avoids search by allowing
  floors only and no alternatives.
- §3.3 concludes "floors, not ceilings" but doesn't say that this is also what
  keeps matching a check. Option A then allows a full range.

*** F3. A match is redone with no memory of the last pick: the lockfile question, asked as "wait or switch"
- Where: §4.3 C, Several builds; Q5.
- Quote: "whether the first's arrival switches builds".
- The match runs again whenever =code= reads again: a loader is placed, or a
  target node is written. Nothing records the pick, so the build a process runs
  can flip as loaders come and go. Example: =peer= moves from =wasi-p1= to native
  when =loaders/aarch64-linux-gnu= is placed, then back when it is unplaced.
- Package managers keep the last solution (=pubspec.lock=, =Cargo.lock=). They
  change it only on an explicit upgrade, or when it no longer holds. The paper
  cites no prior art on lockfiles, and no option records the pick.

** No match

| option | no match is            | the person reads                              | can they act on it?                                         |
|--------+------------------------+-----------------------------------------------+-------------------------------------------------------------|
| A      | a refusal at start     | a code; names of the fields that failed       | only if the build's need and the host's value are both shown |
| B      | a refusal at start     | the missing names                             | no: a typo and an absent feature look the same               |
| C      | pending                | a process waiting on a name                   | no: "not yet", "never" and "misspelled" look the same        |
| D      | a refusal (wasm, ELF), or a failure at first use | missing imports; or a =ReferenceError= | for wasm and ELF, yes; for JS, no                    |

*** F4. No option says what a refusal contains
- Where: §4.1 A, §4.2 B, §4.4 D, each "Adds to core/".
- Quote: "a refusal code naming the fields that failed"; "a refusal naming what is missing".
- Naming the field that failed is only the start. Take =peer= on a 32-bit Pi OS.
  For each build, a message the person can act on needs:
  - the field;
  - what the build needs;
  - what the host has;
  - where the host's fact came from (=uname= or the userland, the trap the
    paper itself points out).
- It also needs to say who can act: the host (place a loader, grant a flag), the
  author (ship a build), or nobody (an RP2040's fixed table).
- When two builds fail for different reasons, the message is one reason per
  build. When choices are tied together (F1), it is a chain: "the only JS loader
  here gives ABI 127; every addon build needs 115; so no pair runs." Building
  that chain from the facts used is what PubGrub does. The paper has the facts
  but no shape for the chain.

*** F5. Under C, a typo waits forever
- Where: §4.3 C, No match; §2, Fixed tables.
- Quote: "pending, as today; the loader may yet arrive".
- Nothing distinguishes =loaders/deno-drawin= from a loader not yet placed:
  each finds nothing. The rule that splits "missing" (pending) from "unknown"
  (=no-loader=) is in LOADERS.tex and isn't stated here. With names as open
  paths, a host has no way to tell the two apart.
- A person looking at a pending process cannot tell "place a loader" from "fix
  the spelling" from "this host can never have it". Pub reports "no package with
  that name" apart from "no version fits".
- This "pending" is also not GRAPH's pending, which is a placed id whose node is
  not here, or an =enter= answer, with a route naming what it waits on. A name
  nobody placed reads as empty.

*** F6. The nearest loader wins, even when it refuses
- Where: §4.3 C, Meet; §3.3, Plan 9.
- Quote: "the nearest node at that path that is here"; "the first name found wins, even when it cannot run".
- Under C with A or D, a subtree's own =loaders/native= (an emulating one, or
  =untrusted/js='s worker) can refuse a build that the root's loader would run.
  The refusal names the near loader's fields and never mentions the farther
  loader that fits. =PATH= shadowing and nested =node_modules= produce the same
  confusing errors.
- The paper lists Plan 9's rule as a lesson but never applies it to its own
  stacked options.

*** F7. Hiding the skipped builds goes against the core's own rule
- Where: §4 Options, opening; Q7.
- Quote: "None says that the builds it passed over, and why, can be read".
- GRAPH.tex, Reads are lists: "no one is handed one of several without
  knowing". A read's =from= records the members that =enter= refused before the
  one it took. Picking one build of several has the same shape, though it is not
  a read. Q7's first choice ("only the one picked") would break that property
  in spirit, and the paper doesn't say so.
- pip is the warning case. Its "from versions: none" hides the wheels it skipped
  and their tags, which appear only with =-v=.

*** F8. D's failures come after start, in the runtime's words rather than in terms of needs
- Where: §4.4 D, Meet.
- Quote: "the code runs and fails at first use".
- For "any JS" and firmware names, the person sees "Deno is not defined", or a
  trap from a shim, never "needs deno". For a hard need, D gives the least
  readable "why not" of the four, although the walk grades D "works best" for the
  "better with, runs without" case.

*** F9. A doesn't say what the matcher does when the target node is empty, pending or has several members
- Where: §4.1 A, Host.
- Quote: "a target node, or a list best first".
- Under GRAPH, a read of the host's target can give nothing (not written yet), a
  pending item, or several members in slot order (an emulation layer's target
  stacked in front). A doesn't say which one the matcher takes, or whether a
  pending target counts as no match or a wait.

** Versions, levels, ranges

*** F10. Versions have no syntax and no order
- Where: §4.1 A, example.
- Quote: ="libc": ">=2.36"=, ="version": "6.6"=.
- As strings, kernel 6.10 sorts before 6.6. macOS, glibc, Android API levels
  and browsers each order their versions differently. The range syntax (=>==,
  caret, intervals) is never given.
- The example's =libc= isn't one of the decision's fields (arch, CPU features,
  OS and a version range, ABI or API version, object format). The host's
  ="version"= doesn't say what it is the version of.
- Pub started with one total order on versions and one form of range. Without
  those, A's "in the range" can be neither checked nor explained.

*** F11. A allows ranges with ceilings, while the paper's prior art says floors
- Where: §4.1 A, Program; §3.3 Java, Android, Erlang.
- Quote: "OS and a version range"; "floors, not ceilings".
- A ceiling on a host version refuses an old build on every newer host. A build
  that says "macOS up to 15" stops on 16 even though it would run there. Android
  discourages =maxSdkVersion= for this reason. Dart 3's pub reads an SDK upper
  bound of =<3.0.0= as =<4.0.0= for packages already on null safety, because
  ceilings on the platform aged badly.
- The paper takes ranges from the input decision without saying whether a
  ceiling is ever honoured.

*** F12. The line between names and relations is not where the paper draws it
- Where: §4.2 B, Meet; §4.1 A, Meet; §4.4 D, Meet.
- Quote: "So B compares names, as C does, which the input decision rules out";
  "arch, OS, ABI and format equal after aliases"; "symbol versions at most the libc's".
- A matches four of its six fields by name equality. Only features (subset) and
  version (range) are relations.
- B, once cumulative levels are expanded ("a host at x86-64 v3 lists v2 too"),
  already does a subset test.
- glibc's own check, which D relies on, is presence of names. libc defines
  =GLIBC_2.2.5= through =GLIBC_2.36= as names, and =ld.so= checks that each
  required name is defined; it does no "at most" comparison. Python's
  =manylinux_2_28= tag works the same way: the installer lists every older tag it
  accepts.
- So floors can be names. Ceilings and open-ended ranges cannot. The decision
  rules out less than the paper uses it to rule out.

*** F13. Versions folded into names lose both containment and the floor within a series
- Where: §4.2 B, Meet; §4.1 A, Program; §3.3 WASI.
- Quote: "The version is cut into the name (0.2, not 0.2.6), so each match is equality";
  "The API slot takes one value".
- Under B, a program built against additions in =wasi:cli@0.2.6= matches a host
  at 0.2.1, then fails. In the component model, the shortened version only picks
  which host interface to link. Each imported item is then still checked against
  what the host defines, and that check is the real floor. B keeps the
  shortened name and drops the per-item check, which belongs to D.
- When =wintertc/2026= appears, a 2026 host meets a 2025 program only if it also
  lists 2025. That is true only if 2026 removed nothing. Nobody in the paper
  decides whether one dated set contains another. The same goes for
  =wasi:preview1= against 0.2.

*** F14. "A missing field is any": old builds meet axes added later
- Where: §4.1 A, Program.
- Quote: "A missing field is any."
- Raspberry Pi OS's Pi 5 kernel uses 16 KB pages. An aarch64 build that assumes
  4 KB says nothing about page size, so it matches, then stops with jemalloc's
  "Unsupported system page size".
- Each field ermine adds later reads as "any" for every old build. The walk
  notes that "any" and "didn't say" look alike only for "any JS", but it holds
  for every field added after the fact.

** Names chosen with no central authority

*** F15. Nobody owns B's vocabulary, C's names or A's aliases
- Where: §4.2 B, Where it strains; §4.1 A, Meet; §4.3 C, Where it strains.
- Quote: "the names need a vocabulary"; "after aliases (arm64 is aarch64)".
- B's examples come from five sources, or from none:
  - =wintertc/2025= (WinterTC);
  - =libssl.3= (OpenSSL's soname);
  - =isa:aarch64= (LLVM's spelling, or the kernel's?);
  - =deno:ffi= and =pty= (nobody).
  The prefixes look like namespaces, but no one owns them.
- A's example features say =neon=, =crc= (LLVM's spelling). A host that writes
  them from =/proc/cpuinfo= writes =asimd=, =crc32=, so the subset test fails on
  a machine that has both.
- C's names for each combination will be invented host by host: =deno-darwin=
  here, =deno-macos= there. The names ermine defines ("any JS, steps") cover two.
- The prior art leaves out how communities name things without a centre: WIT's
  =namespace:package=, Go's module paths under domain names, reverse-DNS ids
  (Java, Android, Apple UTIs), and pub treating a package as a name plus its
  source, which refuses one name arriving from two sources.

*** F16. Under C, a name means whatever the host says, and the program carries the name without that meaning
- Where: §4.3 C, Host.
- Quote: "places a loader node at each name it answers to, where it wants it".
- Take a program synced from a host whose =loaders/js= is Deno to one whose
  =loaders/js= is a worker. It keeps the name and loses the meaning: no
  =Deno.*=, and a failure at first use.
- GRAPH makes meaning local on purpose ("Configuration is placement"). That
  suits a theme, but it breaks a contract. The paper never asks whether a loader
  name promises anything from one host to the next.

** Compatibility over time

*** F17. A rename is in progress with no rule for old nodes
- Where: §1, Today.
- Quote: "LOADERS.tex still says {"kind": k}".
- Program nodes live in saved and synced graphs, and there is no registry to
  republish them from. Old nodes that say =kind= will meet new hosts, and new
  nodes that say =loader= will meet old peers, indefinitely.
- No option says whether a host accepts both forms, for how long, whether it
  shows that a form is old, or whether it rewrites the node. A rewrite is a
  change in someone's history, under some agent (GRAPH, Changes).
- Prior art: each Sass deprecation has an id, a warning the person sees, flags
  to make it fatal or silence it, and a migrator. Pub marks a package
  discontinued with a named replacement, and retracts a version without breaking
  lockfiles. The paper has nothing like this for loader names, need names,
  fields or steps ops.

*** F18. "Unknown" is treated two ways
- Where: §3.4, item 4; §4.2 B, Where it strains.
- Quote: "Unknown is passed over, not an error"; "an unknown name is not met".
- The agreement in §3.4 is about unknown alternatives, such as an OCI entry or an
  npm condition key. Skipping those is safe, because another entry may fit. An
  unknown need is a different thing: passing over it runs code that needs
  something nobody checked.
- Both directions hit this: a new program meeting a host older than one of its
  fields or names, and an old program meeting a new host. No option says which
  unknowns are safe to ignore.
- Prior art for marking this per need: PNG's critical and ancillary chunks;
  Android's =required="false"=.

*** F19. Steps has no version, and its set of ops will change
- Where: Q11.
- Quote: "Only if the harnesses differ."
- The harnesses will differ the day one of them adds an op; OCaml and Zig have
  no steps at all. Without D's op check, a new op breaks old harnesses and a
  removed op breaks old programs, both at first use.

** Claims the text does not support; prior art described wrongly

*** F20. "None changes SCHEDULER.tex"
- Where: Abstract; §4 Options, opening.
- Q5 (does a better build arriving switch the pick), Q6 (pending or fail) and Q10
  (a running program whose match stops holding) are all scheduler behaviour.
  Whatever answers them belongs in SCHEDULER.tex, or in a rule the scheduler must
  follow.

*** F21. A's grade for several builds
- Where: §4.5, row "several builds".
- Quote: "works: ranked by the host (OCI, Apple)".
- A puts one loader name on the program (in the peer example, =loaders/native=),
  so its list of builds is all one format. "Native, then wasm", the esbuild
  pattern the paper cites, doesn't fit in A. That is the same failure the walk
  marks against D ("fails across formats").

*** F22. The OCI description contradicts itself
- Where: §3.1, OCI image index.
- Quote: "The first matching entry wins, in the author's order"; "the host ranks".
- The spec's first match and containerd's sort by the host's ranking are two
  different rules. The paper states both, then cites OCI in support of host
  ranking in A and in the walk.

*** F23. npm, esbuild, and "names what is missing"
- Where: §3.2; §3.4, item 4.
- Quote: "advisory unless strict"; "no match is a refusal that names what is missing".
- In npm, =engines= is advisory unless =engine-strict= is set. =os= and =cpu=
  are enforced (=EBADPLATFORM=), and an optional dependency that fails them is
  skipped. esbuild's per-platform packages rely on exactly that.
- =esbuild-wasm= is not picked when the native package is missing. It is a
  separate package that a person installs. "Native first and portable last" is
  not something a resolver does there.
- The cited tools mostly don't name what is missing:
  - npm's =exports= error names the subpath, not the missing condition;
  - Android, by the paper's own account, installs and then crashes;
  - Plan 9 picks a name that cannot run;
  - pip says "from versions: none".
  Only Java and WASI hosts name the missing thing. Item 4 describes what the
  paper wants, not what the field does, so F4 is harder than it looks.

*** F24. "Any JS" covers two different sets
- Where: §2, any JS interpreter; §3.2, WinterTC; Q2.
- Quote: "WinterTC's Minimum Common API is a name for that set".
- What every engine has is ECMA-262's globals. The Minimum Common API adds fetch,
  streams, URL, crypto and timers, which QuickJS and Moddable's XS (both in the
  paper's runtime list) do not all ship.
- A program using only =JSON= and =Math= and a program using =fetch= would both
  say "any JS". The runtime keys are a separate WinterTC document, not part of
  the Minimum Common API.

*** F25. Smaller misdescriptions
- Zig's =x86_64-linux-gnu.2.28= is filed under "CPU levels", but it is a libc floor.
- Debian Multi-Arch =same= means "can be installed for several arches at once".
  "Must match" is the default for dependencies, and =foreign= is an opt-out
  declared by the package being used, not the one using it.
- Android's =uses-feature= is a filter on Google Play; the device installs the
  app anyway. The refusal comes from a distributor reading the device's facts,
  which is the paper's "on another device" case, not the host refusing early.
- "GRAPH.tex's lookup, which reads one name": GRAPH.tex defines no lookup. It
  points to LIBRARY.tex.

*** F26. The parts that carry the most weight live in other papers
- C's matching is "LOADERS.tex's search, each step reading the whole path",
  which this paper doesn't describe. F6 depends on it.
- The split between a missing and an unknown loader is in LOADERS.tex. F5
  depends on it.
- "A skip nobody sees is a silent drop" is argued in =build.org=.
- "A program as a folder", Q5's second choice, is LOADING.tex's.
- Pending, error or code from =code(process, view)= is SCHEDULER.tex's.
- From TARGETS alone, a reader cannot judge C's shadowing, C's no-match, or Q5.

* Questions for the designer

Each question starts with a case from the paper. The smaller choice comes first.

1. *Per program or per set.* Tools on one Patchwork page must share one
   Automerge; =deno-js= programs share one set of flags.
   (a) Each program is matched alone, and sharing is the host's arrangement,
   outside targets.
   (b) A need may name the thing another program picked, and matching covers the
   programs placed together.
2. *A pick once made.* =peer= runs on =wasi-p1=; later
   =loaders/aarch64-linux-gnu= is placed.
   (a) Match again on every run, as =code= does now.
   (b) Keep the pick until it stops holding, and record it where a person can
   read it.
   (c) Keep it until a person asks for a new match.
3. *What a refusal says.* Both of =peer='s builds fail on a 32-bit Pi OS.
   (a) A code and the names of the fields that failed.
   (b) For each build: the field, what it needs, what the host has, and where
   that fact came from.
   (c) As (b), plus who can act: the host, the author, or nobody.
4. *The nearest loader refuses.* A subtree's emulating =loaders/native= refuses
   a build that the root's loader would run.
   (a) The nearest wins, and the refusal stands.
   (b) The nearest wins, and the refusal also names the farther loaders at that
   name.
   (c) The search moves on to the next loader.
5. *Not yet, never, misspelled.* The cases are =loaders/deno-drawin=, a name
   missing from an RP2040's table, and a loader still to be placed.
   (a) One pending state for all three.
   (b) Separate states, which means a host can say which names it could ever
   answer.
6. *Ceilings.* A build says "macOS up to 15" and meets macOS 16.
   (a) Floors only.
   (b) Ranges, and a ceiling refuses.
   (c) Ranges, and a missed ceiling runs with a warning the person sees.
7. *Version order.* Kernel 6.10 against 6.6; glibc 2.36; Android API 34.
   (a) One syntax for all versions, dotted numbers compared as numbers.
   (b) Each field's own order, taken from whoever owns it.
   (c) No order: floors written out as lists of names, as glibc and manylinux do.
8. *A field added later.* 16 KB pages on a Pi 5, and old aarch64 builds that
   never mentioned page size.
   (a) Missing means any.
   (b) Each new field gets a default, fixed when it is added (4 KB).
   (c) Missing refuses wherever the host differs from that default.
9. *An unknown need.* A browser page meets =deno:ffi=; an old host meets a field
   newer than itself.
   (a) Refuse, naming it as unknown, which is different from absent.
   (b) Ignore it.
   (c) Each need says which, like PNG's critical and ancillary chunks.
10. *Who mints names.* =deno-darwin= against =deno-macos=; =neon= against
    =asimd=; =isa:aarch64=.
    (a) ermine keeps one list.
    (b) Use outside authorities' names where one exists (LLVM, WIT, WinterTC,
    sonames); ermine names only what is its own (steps, any JS).
    (c) Names are scoped by an owner (a URL or a key), and any community mints
    its own.
11. *A name whose meaning changes.* A host moves =loaders/js= from Deno to a
    worker; =kind= becomes =loader=.
    (a) Names promise nothing.
    (b) A published name keeps its meaning, and a change takes a new name.
    (c) Old forms are still accepted, shown as old, with the new form named.
12. *Any JS.* One program uses only =JSON= and =Math=; another uses =fetch=.
    (a) One name, meaning the language only.
    (b) Two names: the language, and WinterTC's dated set.
    (c) WinterTC's sets only.
13. *Dated sets.* =wintertc/2025= meets a 2026 host; =wasi:preview1= meets a 0.2
    host.
    (a) No containment: a host lists every set it meets.
    (b) Each set's owner says what it contains.
    (c) ermine says.
