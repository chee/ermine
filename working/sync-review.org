#+title: sync and transactions review, 2026-10-09

LLM reviews of layers/subduction/SYNC.tex and working/TRANSACTIONS.tex, one
through Brooke Zelenka's area (authorization, Keyhive, encryption) and one
through Alex Good's (Subduction, Sedimentree, Automerge). Simulated lenses, not
their views. Both checked claims against local checkouts: subduction 2566cbf,
keyhive_core 0.6.0, beekem 0.4.0. SYNC.tex's account of Subduction (depth,
FragmentRequested, lower digest on a CommitId collision, minimizing) is
accurate.

* Both found
- A held transaction can hold a document forever on defaults: =hold= is none;
  Keyhive answers pending, never no, to a non-member, so "B private" acts like
  "B's key late" forever; a signer's =docs= counts can't be checked; a crash
  part way; a junk commit under a real stored id "may still come" and never
  does. Fixes offered: a finite =hold= default; pending with no peer offering
  the document → not waited for; a count the tree can't reach → will not
  come.
- What a relay sends is stored whoever authored it; ermine judges only after
  taking in. A junk fragment with a low head and the real ids as checkpoints
  makes minimizing drop the real fragments and commits: a late joiner never
  gets them, and nothing shows it. subduction_keyhive's own policy
  (=authorize_put_with=) requires the author to have Edit.

* Authorization lens
- Blocking: nothing enforces Edit. A reader (who holds the epoch key) or a
  revoked editor can write a longer chain and own a value, or place an id first
  in a slot and redirect walks. =revoked= on an item doesn't protect a program
  reading by path. Fix: show them, never let them win (sorted behind every
  authorized head; never the member a walk takes).
- Blocking (to verify): a device added later may not decrypt history before
  its grant (beekem rebuilds with its own leaf; causal envelopes are
  test-only in 0.6.0). Test: add a member, decrypt an old commit.
- Should: =docs= keys and the clockument node leak through the weakest lock
  (an unlocked document touched with a Keyhive one publishes the latter's id
  and counts; if touched first, its commit names). Suggests blinded keys.
- Should: a relay also sees each commit's issuer (= signer = Keyhive identity),
  the lock record's =made=, and Keyhive membership messages in the clear.
- Should: one key in two running instances likely forks the Keyhive leaf
  secret (to verify).
- Should: revoking through a group keeps Relay-reachable devices decrypting
  (=Keyhive::revoke_member= vs =Document::revoke_member=); report upstream.
- Consider: Keyhive's revocation =after_content= is a ready slot for the cut;
  one upstream call to set content heads. Drop the clockument node (costly,
  for showing only). One Keyhive document per access boundary, not per node.
  keyhive_core needs std: microcontrollers only have =unlocked=; a small
  symmetric-key lock would fit LOCK.tex.

* Sync lens
- Should: two sides never become one (a write settles only the first head);
  Automerge's =pred= resolves on the next write. Settle what the writer read.
- Should: every write's side is kept forever (=sync.ts= =known=); keep heads'
  sides only, replay on demand.
- Should: nothing makes a missing fragment; storing a commit and adding its
  fragment are separate writes; the TS walk skips the "taken out" step.
- Should: fragments don't compact: depth 2 ≈ 65k sealed changes ≈ 13 MB of
  per-change overhead; write signers/agents/sites once per fragment.
- Should: =connect.ts= rescans every commit of every followed document each
  round; use =onRemoteHeads= and the batch calls.
- Should: the maker follows every clockument forever; push once, don't follow.
- Should: a crash part way: journal a request's sealed blobs as one record
  before adding them.
- Consider: one commit per document per request (Automerge's change is its
  transaction) removes one-document transactions and "held with" inside a
  document. =docs= grows quadratically (100 children ≈ 1.5 MB); carry it on
  one commit per document. Bound the waiting list in memory.
