#+title: Rebasing values, after eg-walker

The second way to merge a shared value that SUBDUCTION_SYNC.tex (Values)
plans. Sides stay the default; this is an opt-in per node. Built as an
experiment beside the first one (plans/sync-experiment.org). Nothing here is
decided.

* eg-walker in brief
Gentle and Kleppmann, EuroSys 2025; reference: github.com/josephg/eg-walker-reference.

- Each op (insert one element at i, delete the element at i) is stored as
  its maker made it: positions in the document *at its parents*, plus its
  parents. The event graph is the commit DAG.
- To merge, walk the ops in any topological order, keeping a CRDT state
  only for the walk (thrown away after). Each item in that state has two
  states:
  - *prepare*: as at the parents of the op being walked: not yet inserted,
    inserted, or deleted n times. The op's own positions are read here.
  - *effect* (end): as once everything walked so far is merged: inserted or
    deleted. Positions to emit are read here.
- Before walking op e, *retreat* the ops in the prepare version that are not
  ancestors of e (reverse order: undelete, then uninsert), and *advance* the
  ancestors not in it. Then apply e: a delete takes the prepare-visible item
  at its position; an insert finds its place among concurrently inserted
  items by Fugue's rule (origin left, right parent, tie by id).
- Speed comes from two things not built here: replaying only from the last
  version every side shares (placeholder items stand for what came before),
  and dropping the state at *critical versions* (where history is a line).

* ermine's patches mapped onto it
Each commit is replayed in the *ascending agreed order* (lower Lamport first,
then lesser name): a topological order every device computes alike, so the
merge is a pure function of the set of commits. Each of a commit's patches
is replayed on the one before.

| patch                          | pieces in the replay                       | concurrent with another                                       |
|--------------------------------+--------------------------------------------+---------------------------------------------------------------|
| splice of a string             | a sequence of code points                  | as eg-walker: both kept, Fugue order, deletes once            |
| splice of a list               | a sequence of elements, each a container   | as strings; a path [.., i] follows the element, not the index |
| splice of bytes / typed array  | a sequence of octets / numbers of the kind | as strings                                                    |
| set of a map key               | a register per key: one write per set      | the write first in the agreed order wins                      |
| snapshot                       | a write to the root register               | as a set: the first in the agreed order wins                  |

- *Paths*: followed at prepare, so a patch lands in the container its maker
  saw. A container is named by the write or list element that made it.
- *Sets of one key*: the first in the agreed order (highest Lamport, then
  greatest name) wins, among visible writes at prepare and among all at the
  end. A causal successor always has a higher Lamport number, so a later
  write always beats the one it was made on; only concurrent ones are
  decided by name. This is the same order the sides use, so the winner is
  what the first side would have shown.
- *Sets under a path a concurrent change deleted or replaced*: they land in
  the old container, which the end value no longer reaches. Their effect is
  gone (Automerge does the same).

* Snapshots, and not deciding
A snapshot can't be rebased: it has no positions, it replaces. Two choices:
stay a side, or win by order. Built: *both, split by job*.
- *The value wins by order.* A merge must be one value, the same on every
  device, and the graph has to hold something a write applies to.
- *What it beat stays readable.* For every head, the replay of that head
  alone says which patches have an effect; any of them with no effect in the
  merge is *dropped*. While there are several heads, the node reads as:
  1. the merge, with =heads= and =dropped: [{commit, patch}]=;
  2. then each head that lost something, as its own side (=commit=, its
     value alone, the change that applied it here).
  A write here applies to item 1 and settles them, as in sides.
A patch is dropped only when some head never saw it: if every head made on
its commit takes it out between them, they saw it and wrote over it, so its
loss is theirs, not a concurrent one's. (Without this, a set that both heads
saw and one replaced was named as dropped, and the other head shown as a
losing side.)
So the rule of thumb holds: nothing lost is hidden, and the choice is made
only where one value is needed. The same goes for every drop, not only
snapshots: a concurrent set of one key, a set under a deleted key, a splice
in a list element deleted concurrently. Concurrent splices of one sequence
drop nothing and read as one item.

* How it plugs into share.ts
=share(api, { id, address, merge: "rebase" })=. Default ="sides"=: unchanged.

- *The blob says it.* Every commit of a rebased node carries
  =merge: "rebase"= (commit.ts), and with two parents or more names *no*
  =base=: its patches apply to the merge of its parents, not a side. A
  commit of the other kind is refused (=CommitError=). Blobs without the
  field are byte-for-byte as before, so their names are unchanged.
- *Local write*: parents = the heads, as now; value = its patches on the
  graph's value, which is the merge of the heads.
- *Arrival*: Lamport checked as now; its patches must apply to the merge of
  its parents (that is the =patches= check). The graph is then written:
  - its own patches, when its parents are exactly the heads the graph held;
  - else a snapshot of the merge of the new heads.
- *Reads*: one head → as now (=commit=). Several → the merged item, then the
  losing sides, as above.
- Merges are cached by head set; the replay is from the start each time.

* What was built
- =ts/src/sync/rebase.ts=: =rebase(start, events)= → ={value, kept}=;
  =merge(start, log, heads)= → ={value, dropped, losing}=; =history=,
  =ascending=. The list part is the reference's integrate() (its Fugue line,
  not FugueMax), with ids =[replay index, patch, element]=.
- =ts/src/sync/commit.ts=, opt-in only: =Body.merge?: "rebase"=; =commit()=
  takes a fifth argument =merge?: "rebase"= (which forbids =base=, writes
  =merge=); =open()= accepts =merge= only as ="rebase"=, and then refuses a
  =base=. =KEYS= gains ="merge"=.
- =ts/src/sync/share.ts=, opt-in only: =ShareOptions.merge?: "sides" |
  "rebase"=; =MergedItem= (=heads=, =dropped?=); the rebased branches in the
  local write, =apply= and =sides=; a refusal of a commit of the other kind
  in both modes (a sides node refuses a rebased commit).
- =ts/test/rebase_test.ts=, 22 tests: strings in code points, no
  interleaving (one splice each; and typing forward, backward and between
  two characters, a commit per character), an insert beside a concurrently
  deleted emoji, a replaced write both heads saw is not dropped, double deletes, a delete overlapping an insert (the insert
  stays), deletes and inserts on three devices in all six orders, lists /
  bytes / float32 / int64, a path following a moved list element, set
  winners and drops, sets under deleted and replaced keys and in deleted
  list elements, snapshots, patches in order, and four through share.ts,
  the last three devices with commits delivered shuffled and twice (12
  seeds × 20 writes). A fuzz (30 seeds × 25 commits) checks eg-walker's
  law: every commit's value equals its patches on the merge of its parents,
  the merge doesn't depend on input order (three shuffles each), and every
  dropped patch is one some head never saw. The three-device share test also
  checks each device holds the replay of every commit's body.
- An insert lands just after its left neighbour, before items already
  deleted there, as in the reference: "0123456789" with 3..6 replaced by C
  and D put between 4 and 5 concurrently reads "...CD7...", not "...C7D...".
- Whole ts suite: 437 passed, 0 failed, 1 ignored.

* Not built, and choices for chee
1. *Where the mode lives.* Built: in every blob. Or: a property of the node
   (only the first commit says it; or the placement does). In every blob
   costs ~14 bytes and makes each commit say how to read its patches.
   chee 2026-10-07: set at node creation, to start with. The built version
   writes it in every blob; moving it to the first commit is not done yet.
2. *Small patches into the graph.* Arrivals off the held line are written as
   snapshots. eg-walker's real output is effect-positioned ops: replay the
   held version, then the new commits, emitting splices and sets at the
   end positions. Readers would then see small changes. Next to build.
3. *Speed.* Every merge replays from the start. Replaying only from the
   heads' last shared version (placeholders), and fragments
   (SUBDUCTION_SYNC.tex) as starting points, both wanted for long texts.
4. *Equal concurrent sets* are reported as dropped, since the two values
   are different containers that later patches can tell apart.
5. *No move.* A list element moved (deleted and reinserted) while another
   device edits inside it loses the edit, reported as dropped.
6. *Fugue or FugueMax* for the insert order; the reference runs Fugue.
7. *Sides mode unchanged*: share.ts still holds the last-applied side, where
   SUBDUCTION_SYNC.tex says the first in the agreed order.
