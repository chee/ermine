#+title: Sync, first experiment: results

The experiment from SUBDUCTION_SYNC.tex (Open) and plans/subduction.org: one
node's value, two graphs in one Deno process, commits passed by hand. No
network, no Subduction library, no core change. Nothing here is decided.

* What was built
- =ts/src/sync/commit.ts=: a write to a node's value becomes a commit
  ={hash, blob}=; =open= checks the hash and the blob's shape; =agreed= is
  the order of heads.
- =ts/src/sync/share.ts=: =share(api, {id, address, agent?, time?})=, a
  wrapper for one node. Adds =receive(commit)=, =commits()=, =heads()=,
  =waiting()=, =body(hash)=, =hashOf(time)=.
- =ts/test/sync_test.ts=: 10 tests, (a)–(g) of the brief and a few more.

** The blob
Deterministic CBOR (=cbor.ts=: sorted keys, shortest floats, strict decoding),
a map of:

| key     | what                                                                 |
|---------+----------------------------------------------------------------------|
| kind    | "write" (only writes yet)                                            |
| node    | the node's id                                                        |
| patches | the write's patches, fields left undefined dropped                   |
| agent   | as the change has it                                                 |
| process | only if the change has one                                           |
| cause   | only if the change has one                                           |
| parents | 32-byte byte strings, sorted bytewise, none repeated; [] for the first |
| lamport | 1 + the parents' highest, 1 with none                                |
| base    | only with 2+ parents: the parent the patches apply to                |

Not the time, not =ephemeral= (ephemeral writes are never commits).
hash = BLAKE3(blob), 32 bytes, from =npm:@noble/hashes@1.8.0/blake3= (already
in the Deno cache, a dependency of Subduction's package): pure TS and
synchronous, so a write stays synchronous; crypto.subtle's SHA-256 is async
only, which a wrapper's write cannot wait on. Checked against BLAKE3's
empty-input vector. It adds one entry to =ts/deno.lock=.

** How it works
- Local writes: the wrapper subscribes to the node beneath itself, so it
  hears every write to it in the graph's order, from any layer. A
  non-ephemeral one becomes a commit on the current heads.
- Arrival: hash checked; known → ignored; missing parents → held, applied as
  soon as they are known (any order, any repeats); Lamport checked against
  the parents; then written to the layer below with the commit's agent,
  process and cause and a time given here.
- A side's value: its base's value with its patches applied (base = its
  one parent, or the =base= it names, or the node's value when sharing
  began). Replayed once per commit and cached.
- The graph holds the side applied last. A commit whose base is that side is
  written as its own patches; any other as a snapshot of its side (its
  patches were made on another value). So concurrent splices are never
  rebased: each side is the whole value its own chain gives.
- Reading: one head → the graph's item plus =commit: hash=. Several → one
  item per head in the agreed order (highest Lamport first, then greater
  hash first), each with =commit= and the change that applied it here: the
  graph's own for the side it holds, the rest put in by the wrapper.
- A write here while there are several heads names them all as parents,
  and its =base= is the side the graph holds; it settles them to one.

** Where it sits
On top of the scheduler: =share(schedule(graph, ...), ...)=. Arrivals pass
through the scheduler, which stamps the time and runs what they marked.
Over a bare graph it takes =time= (a clock) instead; one test does that.

* Results
All 10 pass; the whole ts suite passes (339, 1 ignored).
- (a) B reads A's value with A's agent and cause (A's site), B's own time
  (=B.time=), and the commit's hash; =hashOf(time)= maps back.
- (b) Out of order and repeated delivery gives the same value, heads and
  item; the first commit releases the two held ones, in order.
- (c) Concurrent sets on two keys: both read two items, in the same order,
  each naming its commit, each a whole side ={title, a}= and ={title, b}=,
  not a merge. Concurrent splices: ="Jello!"= and ="hello world"=, the longer
  chain first. Three devices with three concurrent first writes, heard in
  different orders, read one order everywhere.
- (d) A write over both on A: one item on both, parents both heads, Lamport
  3, base the side A's graph held.
- (e) On B, an arriving commit marks a process reading the node (it runs
  and reads the new item, and later both sides) and a subscription hears it.
- (f) Equal values, equal heads, equal sets of commits.
- (g) B's own change for an arrived commit makes the same hash; a different
  time gives the same blob; a different agent or Lamport number does not.
- A blob not matching its hash, or a wrong Lamport number, is refused and
  changes nothing. An ephemeral node's writes make no commits.

* What the paper did not determine
1. *Which item is first.* "Puts the other sides in front of the graph's own
   item" and "in the agreed order" agree only if the graph's side is always
   last in that order, and it can't be: the graph's last change must be the
   one that set its value, and each arrival is a change (so readers are
   marked). Built: all heads in the agreed order, the graph's own among them.
   The direction of the order (highest first?) is mine.
2. *What a write over sides patches.* The graph holds one side, not
   necessarily the first item, so a set or splice "over both" lands on that
   side (test (d): on A it landed on B's side). Replaying it elsewhere needs
   to know which, so I added =base= to merge commits. Perhaps a write over
   sides should be a snapshot, or the graph should hold the first side.
3. *The graph's value differs between devices while sides are open* (each
   holds its last-applied side); reads agree.
4. *Writing what arrives needs an address.* CORE writes only by path; the
   sync wrapper knows a document id. Here it is given an address. =release=
   is the only by-id operation; sync may need another, or a place per
   mounted node.
5. *Beneath the wrappers, or through them.* Beneath the scheduler a wrapper
   can't take a time from its clock nor have marked readers run (the TS
   scheduler learns only from its own changes). On top, arrivals pass
   through everything below, including =protect= if present. The paper says
   =keyhiveprotect= checks arrivals; plans/subduction.org says protect never
   sees them.
6. *Process ids collide.* Seen: A's writer and B's watcher were both
   =@7-kabab=; the arriving change said =process: @7-kabab=, so on B it
   looks made by B's own watcher (which CORE lets a process pass over as its
   own). The scheduler's agent also carries A's local time
   (=program: {node, time}=). The process was kept as the plan says.
7. *The start.* The node's value when sharing began must agree on both;
   the placement that made the node is not a commit yet.
8. *Local paths in hashes.* A site cause is =file:///Users/...=, now in a
   shared, hashed blob.
9. *The time map.* Records still name local times; =hashOf(time)= is kept
   beside them in the wrapper (the "or kept beside it" of the paper's last
   section), not in the change.
10. A bad commit held behind a good one is dropped when the good one
    arrives, the rest still apply, and that =receive= throws; what waits on
    the bad one stays held for good. The paper says nothing of refusals.
