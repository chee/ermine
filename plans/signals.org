#+title: ermine/signals: Solid-style handles inside a program

A small library a program imports. It is not core and changes nothing in
the spec. It makes the nodes a program keeps its state in, and hands back
callable handles: =count()= reads and =count(v)= writes. These are the same
handles =ermine/dom= renders, so ={count}= works in JSX. Code will go in
=ts/src/signals/=. Nothing is built yet.

* The shape

#+begin_src tsx
import { input, keep, source, signals, show, me } from "ermine/signals"

// Module level: only names and first values. No context and no graph yet.
// Processes running this program share the module, so nothing per-process
// is kept here.
const my = signals({
  count: input(0),        // made under this process; gone when the process goes
  todos: keep(null),      // made at ./todos if nothing is there; outlives the process
  doc:   source("doc"),   // found by lookup, nearest first; never made
})

export function compute(ctx) { const { count, doc } = my(ctx); ... }  // reads, tracked
export function effect(ctx)  { const { count } = my(ctx); ... }       // makes, writes
#+end_src

Everything comes from =ctx=; there are no globals. =my(ctx)= tells the two
parts apart by what the scheduler hands it: an effect's context has
=lasting=, and a compute's has =pending=. The compute and the effect use the
same declarations, so they cannot disagree about a name or a first value.
That is why the declarations sit at module level, not inside each part. The
same-thread loader lets one module export both =compute= and =effect=
(loaders.ts), so they share it.

* The three kinds of signal

| word            | node                                  | where by default    | when it is made                     | when it goes                       |
|-----------------+---------------------------------------+---------------------+-------------------------------------+------------------------------------|
| =input(v, at?)= | ephemeral                             | =<pid>/<key>=       | by the effect, if the slot is empty | with the process (scheduler kill)  |
| =keep(v, at?)=  | ordinary                              | =./<key>= (beside)  | by the effect, if the slot is empty | never; a later process finds it    |
| =source(name)=  | whatever the lookup finds             | the nearest =name=  | never                               | not ours                           |

*The default is =input=, which is ephemeral.* The reasons follow from the
rules:
- A restarted process gets a new pid (SCHEDULER, Starting again). An
  ordinary node under =<old pid>/= would be kept with the dead process node
  and never found again. So "ordinary, under the process" would leak and
  persist nothing. That rules it out.
- Ephemeral nodes are let go with their process (SCHEDULER, Ephemeral nodes).
  This is Solid's createSignal: state lives as long as its owner. A restart
  starts from the first values, as a remounted component does.
- An ephemeral node may hold a live value, such as an element or a stream,
  and an ordinary one may not.
- Anything meant to outlive the process is a file other people can find, so
  it should sit beside the process (=./todos=), not under it. That is =keep=.
  Two processes in one directory that keep the same name share one node, as
  two programs share a file. This is on purpose.

Two limits follow from CORE:
- A =keep= under an =input= is invalid, because an ordinary node cannot sit
  inside an ephemeral one. The error passes through to the caller.
- =at= is a path from =.=, for example ="../shared/count"=. The parent must
  already be there; v1 makes no folders on the way.

* Making: idempotent, through the effect

In the effect, =my(ctx)= checks each =input= and =keep= before making it:
- It checks for the slot, not the value, so a mounted node that is not here
  yet counts as there and gets no second id beside it. The check is a
  =lasting.directory(parent, name)=. Lasting reads are not kept and not
  recorded (SCHEDULER, lasting), which suits a check whose only question is
  "should I make it?".
- If the slot is empty, it places a node through =ctx.api=: an =input= with
  ={ephemeral: true}=, and a =keep= as an ordinary node, each with the first
  value and a random id. Because it goes through =ctx.api=, the placement is
  in the run's record, as the effect's change.

Every effect run calls =my(ctx)=, and from the second run on the slot is
there, so it places nothing. The same handle path reaches the same node, run
after run.

On the first run the compute runs before anything is made. A handle that
reads nothing gives the declared first value (=input= and =keep=), so the
compute does not stall. Its read of =<pid>/count= tried that slot, so the
effect's placement marks it (CORE, Changes). The compute then runs once more
and returns the same value, and the record shows why. A =source= with
nothing there gives =undefined=, and the compute returns =pending=, as
anywhere else.

* The handle

A signal /is/ an =ermine/dom= Handle (=ts/src/dom/handle.ts=, =node(api,
path)=), so =isHandle= is true. The library builds it over a small
interface that sends each operation to the right place, and adds three words.

| call                       | in the compute                                     | in the effect, its handlers, timers, views                    |
|----------------------------+----------------------------------------------------+---------------------------------------------------------------|
| =s()=                      | read through =ctx.api=: recorded, tracked          | read through =lasting=: not kept (a peep); a dom scope subscribes |
| =s(v)=                     | refused (=read-only=: a compute only reads)        | snapshot through =ctx.api= while the effect runs, then =lasting= |
| =s(f)=, =s(patch)=         | refused                                            | as shift: =s(f(s()))=; a patch is applied, as =s.write([p])= |
| =s.items()=                | every item: waiting, error, stopped, newer, values | same                                                          |
| =s.names()=, =s.at(name)=  | the children, a handle on one                      | same; =at= gives a signal                                     |
| =s.add(v, name?)=          | refused                                            | places a child, ephemeral under an =input= and ordinary under a =keep=; returns its signal |
| =s.drop(name)=             | refused                                            | unplaces a child                                              |
| =s.path=, =s.api=          | its address from =.=, its interface                | same                                                          |

How a write picks its interface:
- While the effect body runs, a write goes through =ctx.api=, so it is in
  the run's record.
- Once the effect has returned, =ctx.api= answers =stopped=. That error is
  thrown before anything is done, so the handle switches to =lasting= for
  good.
- A write in a =handler(name, f)= call carries ={"handler": name}=. One from
  a timer or a DOM listener carries ={"lasting": n}= (SCHEDULER, What a
  process acts as).

The way back to the graph comes from dom, not from new words:
- =s.items()[0].change= is the header of the change that set the value.
- =change.agent.code.at(-1)= gives the process and its run, handler or
  lasting step.
- =why(el)= from =ermine/dom= answers the same question for whatever element
  shows the signal.

=me(ctx)= is a handle on the process's own node, so a view can show what the
compute returned, waiting and error marks included: ={me}=, or
={() => me().left}=.

* Compute and effect: Solid 2's split, one to one

| Solid 2                                    | ermine/signals                                                         |
|--------------------------------------------+------------------------------------------------------------------------|
| =const [n, setN] = createSignal(0)=        | =count: input(0)=; =count()=, =count(v)=                               |
| =createMemo(() => n() * 2)=                | a function in the compute: =const double = () => count() * 2=          |
| =createEffect(() => double(), d => …)=     | =compute= returns =double()=; =effect= gets it as =ctx.value=          |
| =onCleanup=                                | the effect returns a cleanup                                           |
| =createStore= with paths                   | a =keep= folder: =todos.add(v)=, =todos.at(name)(f)=               |
| =render(() => <App/>, el)=                 | =return show(ctx, el, () => <App/>)= in the effect                     |

*Memos are plain functions of reads inside the compute.* Every read goes
through the compute's recorded api, so the scheduler tracks it already. A
memo that several processes share is already a thing: a program with no
effect (SCHEDULER, a program with no effect is a derived value). It needs no
new word.

* Views: a tracked scope inside an effect (chee's renderer)

=show(ctx, el, fn)= renders =fn= into =el= with =ermine/dom=, over handles
bound to =lasting=. Each bound part is a dom scope that subscribes to what it
read. That is the "new tracked scope inside an effect": a click writes
=count=, the text node updates, and the process does not need to run.

The view has to survive the effect's later runs:
- The scheduler calls the cleanup before every later effect, and also at a
  kill, and the cleanup cannot tell which.
- Tearing the view down each time would rebuild it, and lose focus, on every
  compute change.
- Its subscriptions go through =lasting=, which stops working after a kill.
  So they must be dropped synchronously, inside the cleanup, or they leak in
  the graph, which drops no subscriptions on =forget=.

*Superseded 2026-10-07* (ts/demo/dom.org, Scopes): each bound part is now a
scheduler scope owned by the process, not a subscription. Later effect runs
leave scopes alone; a kill disposes them. =show= is =render(fn, el, ctx)=
once per element and process; there is no pause or resume. What follows is
the old v1, kept for the record.

So =show= did this:
- *first run*: render, and return a cleanup that /pauses/.
- *pause* (the cleanup): unsubscribe every scope while =lasting= still works.
  The DOM stays.
- *next effect run*: /resume/. Resubscribe each scope to the reads it kept.
  The cleanup and the next effect run back to back in one round, so nothing
  can change in between. Then return the pausing cleanup again.
- *kill*: the cleanup pauses, and no effect follows. A microtask sees that
  nothing resumed and takes the DOM out. There is nothing left to
  unsubscribe.

This needs one thing from =ts/src/dom=: =render= has to give back
={ pause, resume, dispose }= rather than only =dispose=, or there has to be
=pause(root)=/=resume(root)= over =track.ts='s scopes. Pause unsubscribes and
keeps =reads=. Resume subscribes again for each read. That is the only point
where the two libraries meet. Everything else already fits, because a
signal is a dom Handle.

** Later (v2): =track(ctx, fn)=, a scope as a child process
Here the tracked scope is a process, so its reads land in records, its order
comes from heights, and it can be seen waiting:
1. The effect places an ephemeral program node =<pid>/programs/<k>= with the
   value ={kind: "closure", compute: k}=.
2. It runs =lasting.start([name], ["programs", k])=. The search starts in
   =<pid>=, so the program is found there.
3. The host's =closure= loader keeps a live table from =k= to =fn=.
4. The child is killed with its parent (SCHEDULER, Children).

It costs one process per scope, which fits a panel or a list but not every
text node. dom's subscribe scopes cover v1.

* Examples

** Counter
#+begin_src tsx
/** @jsxImportSource ermine/dom */
import { input, me, show, signals } from "ermine/signals"
import { screen } from "demo"

const my = signals({ count: input(0) })

// Only reads, tracked. The memo is a function. The value is what the
// process shows anyone who reads it.
export function compute(ctx) {
  const { count } = my(ctx)
  const double = () => count() * 2
  return { count: count(), double: double() }
}

// Makes count on the first run. Draws once. Clicks write through lasting.
export function effect(ctx) {
  const { count } = my(ctx)
  const self = me(ctx)
  return show(ctx, screen(ctx.self), () => (
    <div>
      <div class="big">{count}</div>
      <div class="label">double: {() => self()?.double}</div>
      <button onClick={() => count((n) => n + 1)}>🐇 hop!</button>
    </div>
  ))
}
#+end_src

** Todo
#+begin_src tsx
/** @jsxImportSource ermine/dom */
import { each } from "ermine/dom"
import { input, keep, me, show, signals } from "ermine/signals"
import { screen } from "demo"

const my = signals({
  todos: keep(null),   // ./todos: one child node per todo; outlives the process
  draft: input(""),    // what is being typed; gone with the process
})

export function compute(ctx) {
  const { todos } = my(ctx)
  const all = todos.names().map((name) => todos.at(name)())   // each read is tracked
  return { left: all.filter((t) => !t.done).length, total: all.length }
}

export function effect(ctx) {
  const { todos, draft } = my(ctx)
  const self = me(ctx)
  return show(ctx, screen(ctx.self), () => (
    <form onSubmit={(e) => {
      e.preventDefault()
      if (draft()) todos.add({ text: draft(), done: false })
      draft("")
    }}>
      <input value={draft} onInput={(e) => draft(e.target.value)} />
      <ul>
        {each(todos, (todo, name) => (
          <li>
            <input type="checkbox" checked={() => todo().done}
              onChange={() => todo((t) => ({ ...t, done: !t.done }))} />
            {() => todo().text}
            <button type="button" onClick={() => todos.drop(name)}>×</button>
          </li>
        ))}
      </ul>
      <p>{() => `${self()?.left ?? 0} of ${self()?.total ?? 0} left`}</p>
    </form>
  ))
}
#+end_src

* Words
=signals=, =input=, =keep=, =source=, =show=, =me=. On a handle:
=add=, =drop=, plus dom's =items=, =names=, =at=, =write=. =track= comes
later. There is no camelCase. =input= and =source= are shift's verbs: shift's
=source= is a stream of ops from elsewhere, and here it is a node found
elsewhere. =peep= is what =s()= already is outside the compute.

* Open, for chee
- *Can the cleanup be told why it runs?* The scheduler already knows (its
  =context.kill=). If it called the cleanup with ={killed: true}=, =show=
  would need no pause and resume and no change in dom. It is one argument,
  in SCHEDULER, not CORE. Until then v1 pauses and resumes.
- *Who clicked?* A DOM =onClick= writes as ={"lasting": n}=. To get the host
  to vouch for the person, =show= could send DOM events through
  =handler(name, f)= and the host's =fire=. Should it?
- *Start-up:* making an =input= marks the compute once more, so there is one
  quiet extra run at start, visible in the records. Is that acceptable, or
  should =input= read as its first value without it?
