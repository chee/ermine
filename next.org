#+title: next round

Changes to the papers themselves, for the round after the spec is
implementable. Ideas that can be built on the core as it is live in
IDEAS.tex instead.

* Decide
- Hot reload. A program is one thing with two parts, so compute and effect
  should behave the same when code changes. Keep the program and restart it
  (today, with newer), or swap in place, with a defined handover from one
  effect to the next. Keep a manual save or commit possible, so a program can
  be edited live, for collaboration, without running until it is saved.
- Precedence between competing placements, like CSS =@layer= or Emacs advice
  depth (maybe even =!important=): slot positions plus a wrapper that turns
  ranks into positions, or a rank the graph sorts by (core). Who owns the
  order is open.
- Per-process namespaces, as Plan 9 has: not ruled out. Weigh them against
  "placing changes everyone's view".
- How one host mounts another's graph: a mirror that copies, a served
  subtree, or remote nodes in the core. Comes with Subduction, later.
- Should ephemeral nodes be unique: placed in one slot only? Until then: what
  happens to the children of an ephemeral node held in two slots when it
  loses one holder.
- May a slot of an ephemeral node hold a mount (an id placed with no value)?
- Dead process nodes after a restart: a process node is ordinary and kept,
  but nothing runs it after a reload. What reading it gives, and who unplaces
  it.
- newer is computed beneath protect, so it can name a program the starter
  could not read.
- The agent, process and cause of a cascade's own unplacements (an
  ephemeral node going takes its slots apart, each member its own change):
  the outer change's? At a kill, do they carry the kill's agent and
  {"killed": pid, "by": t} as the kill's own unplacements do?
- Which lasting interface a loader is given for its answers, and the last
  step its writes carry (an effect run's is {"lasting": n}).
- Branching and optimistic state. A branch could be a separate graph, items
  in front, or a matter of history; optimistic state is IDEAS.tex's
  transactions.
- One owner for releasing live things: a process's cleanup, or the list of
  nodes a change let go, not both. Perhaps an ephemeral node goes when the
  process that made it dies, as well as when no slot holds it.
- Rearranging the tree killing processes (SCHEDULER.tex): only unplacing the
  process's own node, or any route change, as today.
- Placed and running coming apart: pausing, for low memory or a knitting
  machine between jobs.

* Core candidates
- One change per slot member, not per slot. Today a slot item can carry a
  change about another member, so "a reader learns who made what it read" is
  false for slots.
- An ephemeral filter: an option for write to reach only ephemeral nodes and
  for read to skip them, chosen by the scheduler when it binds a process's
  interfaces. No wrapper can write to a union member other than the first.
  The no-core alternative is mounting the stored node under a name of its own.
- Lookup out of the core, as a library of directory reads, as the
  scheduler's program search already is.
- The optype: whether the graph should see a small canonical form, like
  DAG-CBOR, that each host enriches. Values beyond JSON and ephemeral nodes
  cover most of this now; what's left is whether the canonical form is what
  the graph itself operates on.
- protect's rules in the graph, addressed by place, with the scheduler
  mounting the graph chrooted beneath itself so the protector sits where only
  the user sees it.
- References: a value that names a node by id, ={"/": {"ref": id}}=,
  followed by mounting it. Taken out 2026-10-07 for now.

* Decided 2026-10-07, after the hacker review (write in the next papers pass)
- Chroot is about naming, not authority: a chrooted process that protect lets
  read a node may mount it. Ids must not be guessable (no node called "root");
  ids will be keys from signers and derivations, which keyhiveprotect needs.
- A refused read does not track, for now (so later changes there do not mark
  the reader or hand it their contents). Idea: a refused read might give a
  different value that updates later.
- protect is asked about start, with the program and loader ids. "If someone
  can write above you in a place you can see, they own you" is a visibility
  matter more than a bug.
- The scheduler marks its own changes in the agent, which programs can't set
  (e.g. a last step {"kill": pid}), so a kill can't be spoofed by a cause.
- A handler call keeps the process's actor, and records the person who acted
  beside it, not as the actor.
- Ids in shared untrusted systems will be keys; squatting on predicted ids is
  not the graph's job.
- Done: ephemeral nodes are unique (one slot), cheap, and belong to a process.
- Declined for now: unplacing as rm -r for every node; losing undo by
  re-placing an id is close to a dealbreaker. A move operation may still help.
- Idea: protect as a process node at the root that the scheduler places, and
  always uses the one at its root.

* Subduction, chee 2026-10-07
- Not Keyhive beside protect: a new keyhiveprotect, a protect that decides
  with Keyhive.
- Make time not matter across devices: a local arrival order for runs and
  records, and a global identity for changes (a commit hash, or signer plus
  counter).
- Concurrent positional patches: like the Automerge–CodeMirror binding, a
  CRDT underneath; study eg-walker-style rebasing for values and a small CRDT
  for slots, with concurrent sides read as items.
- History comes from Subduction; revocation replays from it.
- A placement that makes a node across two trees: split into the child's
  first commit and the parent's placement that depends on it, or transactions.
- chee likes all three for merging (an Automerge document in a node; eg-walker
  rebasing; a CRDT for slots, with concurrent sides as items). All three fit
  above the graph: the sync process merges and makes ordinary writes and
  placements, as the remote change's agent and cause; a sync wrapper shows a
  value's other side as an item in front. No graph change.
- Transactions on top: the sync process holds a transaction's parts until all
  have arrived, then makes them in one batch; or holds them as items in front
  (IDEAS.tex, transactions).
- Sync is a process node, like everything that does something. The page
  loads ermine first, and everything else lives in ermine; the boot image
  starts sync. As a process it may make ephemeral nodes for peers' cursors.
