#+title: api trials

Small models write programs against several api designs. Each design has a one-page cheat sheet
and a thin adapter over the real process api (@ermine/ermine), so every program really runs. A
check per task says whether the program did the job.

* Layout

- =designs/<x>/adapter.ts=: the design's words, made from a process's real api. =designs/<x>/sheet.md=:
  its cheat sheet (at most 60 lines, L's 63; the same 8 sections in the same order, the same
  examples on the same lamp). =designs/<x>/sheet-whole.md=: the same sheet with "A whole program" at the top
  (one runnable lamp program, under 20 lines, solving no task; checked by =lib/whole.ts=).
  =designs/index.ts= lists them: a (words), b (call), c (hooks), d (methods), e
  (explicit-e), f (me), g (invented), g2 (update), g3 (produce), h (call-global), i
  (call-verbs), j (smallest), k (solid), l (imported). =designs/l/ermine.ts=: the module L's
  programs import their words from.
- =tasks/<task>.ts=: a statement (design-neutral, exact names) and its check. counter, derived,
  todos, service, slow, save; then five harder ones: view, pending, memo-send, shared,
  after-await; then components, a program of two files (below). service changed under the
  references on 10-25 (a setup runs once now): rounds one to nine's service scores were taken
  under the old rerun (finding 4).
- =lib/trial.ts=: one trial (a fresh ermine, the program at =/code/trial= through its adapter,
  started with cwd =/work=, =show= kept), the judge (={ ran, correct, notes[] }=), loading a file.
  =lib/hints.ts=: a run's facts turned into instructions in the design's words (below).
  =lib/handles.ts=: B–D's handles. =lib/contexts.ts=: what E and F share (paths, the context stack,
  lifetimes, coded errors, waiting); G uses its paths and waiting too. =lib/jsx.ts=: =h=, a
  =Fragment= and a string renderer, for .jsx programs; a function component is an instance, an
  early effect re-rendering by itself (the components task, below). =lib/importmap.ts=: "ermine" made importable (below).
- =reference/<x>/<task>.ts= (=.jsx= for view; =reference/<x>/components/= holds =main.jsx= and
  =counter.jsx=): a reference program per design and task (168: 14 designs × 12 tasks).
- =run.ts=: the runner.

* Running

#+begin_src sh
deno run -A playground/api-trials/run.ts <design> <task> <file>     # one program: a JSON result
deno run -A playground/api-trials/run.ts --all <dir>                # <dir>/<design>/<task>/<try>.ts|.jsx|/main.jsx
deno run -A playground/api-trials/run.ts --prompt <design> <task>   # the sheet, then the task
deno run -A playground/api-trials/run.ts --prompt <design> <task> --sheet whole  # sheet-whole.md
deno run -A playground/api-trials/lib/whole.ts                      # each whole program runs
#+end_src

=--all= also takes =<dir>/<design>/<task>.ts= (or =.jsx=) as one try (so =--all playground/api-trials/reference=
runs the references). A task of several files (components, =files= in its task): a try is a
folder, =<dir>/<design>/<task>/<try>/main.jsx= beside its other files (=counter.jsx=), or the
task's folder itself holding =main.jsx= (one try). =--prompt= then says to write each file in its
own block. Every program runs with "ermine" importable: deno's =--import-map= takes the place of
the config's imports, so lib/importmap.ts writes a map (a temp file: the repo's deno.json imports
plus ="ermine"= → designs/l/ermine.ts); =--all= starts each try under it, and run.ts or
lib/whole.ts started without it starts itself again with it. Hints name a line in the other files
too ("counter.jsx line 3"); a throw from a timer or listener is a note (=uncaught=), not a crash.
Each try runs in its own deno, killed after 20s (a program can loop). It
writes =<dir>/results.json= (every try, with notes) and =<dir>/results.org= (design × task,
passed/tries), and prints the table. =<design>= is a letter or a name.

One program's JSON also has =hints= (a list of one- or two-sentence instructions) and =facts= (what
they came from); =notes= are the judge's, as before. The facts are only what the program could
see, gathered as each trial closes (lib/trial.ts): its errors, each with the program's line (from
the setup's status, the host's sends, each handler's latest call record, unhandled rejections, a
load error); its sends still waiting (=ermine.records.waits()=); its memos and effects pending,
failed or looping (=status=, what they wait on, what their run read); its handlers; what it showed
(and whether a promise was shown); and the nodes it wrote holding ={ value: x }= (or ={ count: x }=
at =./count=) or a promise. Never the check's wanted values. lib/hints.ts turns each into an
instruction: error codes (ermine's, the adapters', JavaScript's), named in the design's words (its
memo, its read, its write) and naming the program's line. The repair scripts read =hints=.

A program is =export default function (api) { … }=. Every design gives =show(text)= (E: =e.show=,
F: =me.show=, G–K: a global, L: imported from "ermine"); the save task adds =save(text)=, shared
=check(text)=, after-await
=title(url)= (a task's =given=; =--prompt= says where: "in =api=", "on =e= (e.check)", "on =me=",
"as a global and in =api=", L: "as an argument of the program's function"; for E and F it also
writes the view task's =show(= as =e.show(= /
=me.show(=). Checks write and read only real nodes: =./x= is =/work/x=. The slow task's value is
written over a node the program made there, if it made one (E's =e.node= makes it holding null).

* The harder tasks

Haiku passed nearly all of the first six in every design, so they couldn't tell the designs apart.
Five more, each aimed at one trap:

- view :: a counter shown as JSX, =show(<p>count: {…}</p>)=. The trap: the handle in the braces
  (={count}=), not its value. The program is a .jsx file. Deno compiles a .jsx file's JSX as
  classic React (=React.createElement(type, props, ...children)=; the repo's deno.json sets no
  =compilerOptions=), or as =h(…)= under a =/** @jsx h */= pragma: lib/jsx.ts puts =h=, =Fragment=
  and =React= ={ createElement: h, Fragment }= on =globalThis=, so a program needs no import and no
  pragma. An element is plain data; =show= renders it to a string (lib/trial.ts), kept in =shown=
  as =<p>count: 0</p>= and marked as JSX. Rendering: strings (escaped) and numbers as text, a list
  as its items, an element as its tag, attributes and children (a component is called by h, below);
  anything else is =String(it)=, so a handle in the braces shows what it is (=[object Object]= for
  A, D, G; a function's source for B, C, H–K; =[node /work/count]= for F; E's throws NotAValue as
  it renders), and undefined, null and booleans show as words (React drops them; here they would
  hide the bug). The check fails, saying what it saw, on an object, a function's source,
  undefined, NaN, a stale number, or text shown as a string. Its hint (lib/hints.ts) names the
  braced name and the design's read: ={read(count)}=, ={count()}=, ={count.read()}=,
  ={e.read(count)}=, ={me.read(count)}=, ={count.get()}=. JSX in a .ts file gets its own hint.
- pending :: a memo, label, reading /slow/value, a harness memo pending (it returns PENDING) till
  =/slow/in= is written. "loading" while pending, "got: V" after, twice over (ripe, ready); nothing
  else shown on the way. A first trial closes with /slow/value still pending, so the facts (and
  hints) are what a program stuck waiting could see. The statement names none of the designs' ways
  of saying "not ready": A–D, H use =status=; I =getStatus=; E =e.status=; F =me.status=; K
  =isPending=; G–G3 and J's read gives undefined. The hint for a memo waiting on someone else's node
  names that word.
- memo-send :: a memo whose value is a service's answer (=/services/upper=), run four times: the
  service there at start or placed after, answering at once or with a promise (3ms later). The
  check sets ./text twice; nothing but the loud values may be shown (J's memo reads undefined while
  pending: its reference skips that).
- shared :: one program started twice. A process's row is at its code's path, so one code node
  can't run two processes (start refuses: taken): =trial(…, TWO)= places the same program (its
  adapter made again per process) at =/code/trial= and =/code/trial2=, and starts them with cwd
  =/work= and =/work2=. Each has its own =./on/add=; both reach =/shared/list= (the harness makes
  it =[]=). The check sends "a" and "b" at once; =check(text)= resolves after 5ms, so the awaits
  overlap, and a handler that read the list before its await and wrote the whole list after loses
  one. Facts and hints count both processes' own nodes and folders as the program's ("./on/add
  (the second process's)"). G–K's globals are one per realm (finding 15): the second process's
  words overwrite the first's. The references keep their handles from setup, so it doesn't matter.
- after-await :: a handler that awaits =title(url)= (5ms), then writes ./title, pushes to
  ./history and returns the title; sent twice, one after the other.
- components :: two files. =counter.jsx= exports =Counter({ name })=: it keeps ./<name>/count
  (starting at 0), has a handler at ./<name>/on/click adding 1, and renders =<p>count: N</p>=.
  =main.jsx= imports it and shows =<div><Counter name="a" /><Counter name="b" /></div>= whenever
  either changes. The check clicks a twice and b once and wants both counts in the nodes and the
  last view (=<div><p>count: 2</p><p>count: 1</p></div>=, a JSX element). The trap: reaching the
  design's words from another file, in JSX, without the api on a prop. Components are reactive
  (chee, 10-25: yes; until then a component ran only when main's effect showed the tree again,
  and Haiku's programs, written for a React- or Solid-like renderer, went stale or never made
  their nodes). My pick, the smallest over the real api: an instance is an early effect of the
  process's api (=api.early=), made by =h= in the scope open: a node of its own, as a memo is, at
  =.jsx-Counter-N= in the program's own node, holding its text, its SCOPE attribute naming the
  node that drew it. Early, so its first render runs inside =h=. Its f is the render, tracked: it
  calls =Counter(props)= and keeps the element; when what it read changes, that instance alone
  renders again, and show's tree (kept by lib/trial.ts) is shown again whole, so the last shown is
  the tree now. What Counter makes is under the instance, made on the first render and kept
  across the next ones (ermine's own: a memo or effect made again by its owner's next run is
  claimed, a handler placed again keeps its node). An instance is known by its place among the
  components its owner drew in that run or act: drawn again, the same instance (new props, due);
  not drawn, it goes with the run's end or before the next act. Shown from the setup, from an
  effect's act, or built in a memo's f: all work. No process found from the scope open (a timer):
  the component is called plainly. The references still show the tree from an effect that reads
  the counts (written for the old renderer, they pass under both). Where a component's nodes
  live is open: here it uses the paths it is given in props (=name=). How each design reaches its
  words in counter.jsx (the comparison): A–D the api as a prop (=<Counter api={api} name="a" />=);
  E and F a factory, =Counter(e, "a")= in the setup (only the program's e places a handler, only
  the setup's or a run's me answers), giving back the view drawn with the act's e / me passed down
  (=<A e={e} />=); G–K the globals, as they are (one process; finding 15); L imports them.

Every new check settles generously: =rest()= (lib/trial.ts) is a few turns, 40ms of real time,
then a few turns more, after every step.

* The designs: adapter decisions

- A, words :: today's words passed through, only the sheet's (open, read, peep, reads, list, edit,
  memo, effect, method, send, status, why, teardown, PENDING). A word not on the sheet is undefined.
- B, call the handle :: a handle is a function: =x()= read (tracked), =x(v)= replace, =x(fn)= a
  recipe, =x.peep()=. No argument at all is the read (=x(undefined)= writes undefined). A function
  is always a recipe, so a function value can't be written through =x(v)=. A handle reads the whole
  value (no path). memo, effect and method give handles; reads, list, status, why, send take a handle
  or a path.
- C, a hook tuple :: =const [x, patchX] = usePath(p, init)=. The read form is a getter: =x()=
  reads (tracked), =x.peep()= untracked. Why: x has to stay live, and a plain value would be the value
  at setup, stale after. A getter is the shape of the tuple this borrows (Solid's
  =const [count, setCount] = createSignal()=, read by =count()=); the call is where the read
  happens, so where it is tracked; and it can't be taken for a snapshot, as a =.value= can (copied
  or destructured, a =.value= is a stale plain value again). =patchX(v)=: a function is a recipe.
  useMemo and useEffect give =[x]=. method, send, status, why, teardown, reads, list are A's
  (unprefixed: they aren't hooks here).
- D, methods on the handle :: every handle has every method: read, peep, edit (patches or a recipe),
  set, reads, list, info (a handle on the attributes), why, status. memo and effect give the same
  handle. method and send as A's.
- E, an explicit e (E-design.md) :: every function given to ermine gets its own =e= first; four kinds
  (program, compute, act, call) with the designer's table of what each may do (NotHere). An =e=
  checks its kind, its lifetime (Ended), and which =e= runs now (WrongE: another =e= used while a
  compute runs). =e.node(p, start?)= makes with start or null, except in a compute (never made; a
  missing node reads as pending). Handles are a class with no public properties; printing one, or
  =.value .length .map .then=, throws "this is a node, not its value: use e.read(node)". A pending
  read stays pending even when f catches it. =e.call= gives a promise that waits for a handler;
  =e.status= takes a node or that promise. Mine: the current dir is the process's cwd; memo, effect
  and handler names are paths as any, their parent folder made when missing; words take a handle or
  a path; =e.patch= takes ={ op: "remove" | "replace", at, value? }=.
- F, me (F-design.md) :: every callback's first argument is =me=, of four kinds (setup, run, act,
  call). WrongMe: while a callback runs synchronously, any =me= but its own throws. =me.node= makes
  nothing, =me.make= makes. Handles are a Proxy: any property throws NotAValue "this is a node; use
  me.read(node)"; =String(h)= and =`${h}`= are "[node /abs/path]". =me.edit='s recipe must return
  nothing (BadRecipe). =me.write= on a compute's node: Computed; on nothing: Missing ("me.make it
  first"). Outside a run a pending read throws NotReady ("await me.ready(node)"). =me.send= rejects
  with Ended when the sender's =me= ends first, with Failed when the handler throws. Mine: the
  current dir is the process's cwd; a string where a node is used throws NotANode ("a string is a
  path: use me.node(path)"); compute, effect and answer parents made when missing.

- G, what the models invented :: small and large models, given no api (only "a live tree of
  reactive nodes by path; write the code you'd expect to work"), each question answered as most of
  them did. The words are globals (=node=, =derived=, =on=, =show=, =onStop=, a task's =save=),
  put on =globalThis= by the adapter for every trial, whatever =TRIAL_GLOBALS= says; =api= has
  the same words. A bare ="x"= is ="./x"=, the cwd. =node(p, initial?)= makes with initial,
  without one makes nothing. =x.get()= is read (PENDING from a memo with no value yet: undefined);
  =x.set(v)=, =x.set(prev => next)= (a function is always a recipe). =x.watch(fn)= is a hidden
  effect (read x, act =fn(value)=) at =.watch-N= in the program's own node; its f returns PENDING
  while nothing is there, so it first fires once the node is there. =derived= is memo, =on= is
  method, =onStop= is teardown. =x.call(…)= is =sendWaiting= from lib/contexts.ts, as E's =e.call=
  and F's =me.send=: it sends; on PENDING, =whenReady= puts a hidden effect (=.wait-N= in the own
  node) that reads the path until something is there, then sends again; the promise takes the
  handler's reply, or rejects with its error. Mine: =set= on a node not there makes it (=open= with
  the value; a recipe is given undefined), since models write =node("x").set(v)=; =set(fn)= is the
  real recipe, so mutating prev (a draft) also lands, though the sheet says return the next one;
  derived's parent folder is made when missing; cleanup, which the models barely invented, is
  the smallest form: watch's returned unsubscribe and =onStop(fn)=. G has no why and no status.
- G2, update / G3, produce :: G with one change, the same adapter (=invented("update")=,
  =invented("produce")= in designs/g/adapter.ts), so the three differ only in that word.
  =x.set(v)= replaces the whole value, never a recipe. =x.update(draft => …)= (G2) or
  =x.produce(draft => …)= (G3) is the real =edit(x, recipe)=: the recipe changes the draft and
  returns nothing; the patches are recorded from what it did (a push is a splice at the end:
  =range [n, n]=). Why drafts (chee): ermine's writes are patches, which merge under sync, wake only
  readers of the touched paths, and keep why per path; a whole set loses all three. Mine: a
  function given to =set= throws NotAValue naming the draft word (it would be stored quietly as
  the value); what the recipe returns is dropped, so =d => d.push(v)= pushes (the real recipe
  would make the value the returned length); the draft word on a node not there throws Missing
  (nothing to draft from; =set= still makes). Their whole program adds a history list pushed to
  by update / produce in the handler (18 lines).
- H, call-global :: B with two changes, in one adapter with I and J (=called()= in
  designs/h/adapter.ts). The words are globals, on =globalThis= always, and on =api=. A write to a
  node not there makes it: =x(v)= opens it holding v; =x(fn)= gives fn undefined and makes it
  holding what fn returns (nothing returned: nothing made). =x(fn)= on a node there is the real
  recipe under immer's rule (G2's TRIAL_DRAFT_RETURN, always on): the draft changed, its changes;
  untouched and a value came back, that value. So =d => d.push(v)= pushes. Everything else is B's,
  paths too (a bare ="x"= is in the program's own node).
- I, call-verbs :: H with verb-first words, as Solid's createMemo: =createMemo=, =createEffect=,
  =createMethod= (ermine's word "method" kept, only the verb put first). Mine, to keep "every word
  starts with a verb": =status= → =getStatus=, =why= → =getWhy=, and =reads= (a noun here: the
  versions) → =getReads=. Verbs stay: =open=, =list=, =send=, =show=, =teardown=, the handle's
  =peep=.
- J, smallest :: H with every word a program can do without dropped. Kept: =open=, =x()=, =x(v)=,
  =x(fn)=, =memo=, =effect=, =method=, =send=, =show=. Dropped: =peep=, =reads=, =list=, =info=,
  =status=, =why=, =teardown= (and =PENDING=). No task needed a dropped word. Not there yet is =x()=
  giving undefined, as G's: a memo with no value yet (the real read throws PENDING) reads
  undefined. A send to no handler still throws the real PENDING, with no word for it: a memo or
  effect runs again once a handler is there; a setup stays stopped (it runs once). Sections 7 and 8
  say "There is no word for this."
- K, solid :: Solid 2.0's names and signatures on ermine's nodes, as globals ("as you'd import them
  from solid-js") and on =api=. Sources, read 2026-10-25: the solid-js and @solidjs/signals
  2.0.0-rc.18 packages (npm dist-tag =next=, published 2026-10-23): their type definitions
  (signals.d.ts, store/, core/verdict.d.ts, core/action.d.ts) and solid-js's CHEATSHEET.md; the
  docs page v2.solidjs.com/reference/solid-js/reactivity/is-pending (updated 2026-10-20); the
  v2.0.0-beta.0 release notes (github.com/solidjs/solid/releases) through a search. Checked there:
  =createSignal(value, options)= with =[get, set]= and an updater set; =createMemo(compute,
  options)=; async computations; =isPending(fn)=; =latest(fn)=; =createEffect(compute, effect,
  options)=, the split form the only one, effect never comparing, its return a cleanup, =defer=, an
  ={ effect, error }= bundle; =onCleanup=, =untrack=, =flush=; =createStore(value, options)= with a
  draft-first setter (a function only), a returned value used when the draft is untouched;
  =action(generator)=; =refresh(target)=. =name= is a real field of SignalOptions, MemoOptions,
  EffectOptions and StoreOptions (a debug name). Ermine's, marked on the sheet: =name= is the
  node's path (no name: a hidden node, =.signal-N= etc. in the program's own node);
  =createMethod(path, fn)= and =send(path, …args)= (Solid has no word for a handler at a path).
  Mapped: a getter is read (peep inside untrack); a setter replaces, an updater gets the previous
  value; a write to a node not there makes it; =setStore= is edit with the recipe by immer's rule;
  a store is a Proxy reading by property (tracked at that path; a method, symbol or list length
  reads the whole value); =createMemo= is memo; =createEffect= is effect with =equal: () => false=,
  =defer= skipping the first apply, the apply's cleanup run before the next and at stop;
  =isPending= is ermine's status: fn threw PENDING, or a getter it read is pending; =onCleanup= is
  teardown; =flush= is pulse.
  Where K departs from Solid 2.0:
  - a write is seen at once (Solid: after the microtask flush, or =flush()=);
  - =isPending= is also true while a read has no value yet (Solid: that is loading, not pending,
    and goes to a =<Loading>= boundary). Ermine has one pending state;
  - a not-ready read in the setup leaves the setup pending, never run again (ermine's, 10-25); Solid
    has components, =<Loading>= and =<Errored>=, none here (no JSX);
  - =latest(fn)= is =fn()=: no transitions, so nothing is in flight to peek past;
  - =action= runs its generator, waiting on each yielded promise, but its writes are not held till
    it ends (Solid: one transaction); no =createOptimistic=, =createOptimisticStore=, =affects=;
  - NotInApi: =refresh= (a memo can't be asked to run again), =createSignal(fn)= (a writable memo),
    =createStore(fn)= (a projection), an effect's =error= arm;
  - not checked: Solid's dev guard against writes inside an owned scope (a memo or effect compute);
  - left out: =createProjection=, =createDeferred=, =from=, =onSettled=, =snapshot=, =reconcile=,
    =resolve=, =mapArray=, =createRoot=, context, the components.

- L, imported :: A's words (open, read, peep, reads, list, edit, memo, effect, method, send,
  status, why, teardown, show, PENDING), imported from ="ermine"= in any file, with H's one change:
  a write to a node not there makes it (=edit= with a recipe: given undefined, made holding what it
  returns; a whole-value patch: made holding it). chee, 10-25: ermine's words become importable,
  each finding its process from the scope open when it is called, as Solid's createSignal works
  through getOwner(); for "reusable components with code in different files", "with jsx without
  having to put the api on a prop", and so "we could export completely different apis". The
  module (designs/l/ermine.ts) makes the words once for the realm; a registry maps a process's
  scope to its real words, and each word walks up from the scheduler's =getCurrentScope()=
  through =parent= to the first scope registered. The adapter registers the scope open as it runs
  (the setup's) and its parent (the process's), with the trial's scheduler (lib/trial.ts gives
  adapters a third argument, ={ scheduler }=). What reaches the process: the setup, a memo's or
  effect's run and act (a computer under the scope that made it), a handler's call (a scope under
  the one that placed it), a teardown, a component (lib/jsx.ts). Nothing open (a module's top
  level, a timer, a listener, a promise's then, after an await): NothingOpen, "nothing is open
  here: … (a module's top level, a timer, a listener, or after an await)". A program of another
  design importing "ermine": NoModule. The task's functions (save, check, title) are the program
  function's argument (=export default function ({ save })=); show is imported. Mine, beyond A:
  =here()=, the scope open now kept, =back(f)= running f in it (=runWithScope=), as Solid's
  getOwner / runWithOwner; the scope gone: Gone. Without it no L program can write after an await
  (save, shared, after-await would fail), so it is on the sheet, in section 5, marked by nothing
  but its place. Undecided: chee hasn't seen it.

* What the real api made awkward (findings)

1. Context does not survive an await. Today's api is ambient (the scheduler's open scope):
   - after an await in an async memo, reads are not tracked. E and F promise they are; the adapters
     throw NotInApi for any word a compute's =e= / run's =me= uses after an await;
   - after an await in a handler, writes land, but outside the call: =why= names them outside,
     not the call. E and F promise the call's =e= / =me= is still the call. The adapters let the
     writes through (the save task needs them) and say so here;
   - a teardown asked for after an await goes to the process's scope (at stop), not the call's.
     E and F's call (and act) cleanups are the adapter's own lists.
2. WrongE / WrongMe can be checked only synchronously, by the adapter's own stack of contexts.
   After an await nothing knows who is acting, so a closed-over outer =e= / =me= slips through (the
   designers say so too). In A–D a program can't use the wrong context at all: there is none to
   hold.
3. No way to wait, as a promise, on a path or a node. =watch(path)= is not told when a node
   arrives at a path that held nothing, and there is no =ready()=. A send to nothing throws
   PENDING at once. E's =e.call=, F's =me.send= and =me.ready= are built from a hidden effect
   (=.wait-N= in the process's own node): visible in the graph, kept until its scope goes.
4. (Until 10-25: a setup that sent to nothing ran again from the top when the handler came, so its
   effects acted again.) Since chee's "setup is untracked, runs once. like solid." (10-25,
   ermine/ermine's conformance 29-pending-setup-stays), a setup that sends to nothing, or reads a
   memo with no value yet, stays pending and is never run again: to wait, send or read in a memo or
   effect. The sheets' section 6 (and 7: "replaced" is a memo's or effect's only) say so, the
   hints point to a memo or effect, and the service references for A–D, H, I, J and L send from
   an effect (=effect("greet", () => send(…), (reply) => open("./greeting", reply))=).
   The service scores of rounds one to nine were taken under the old rerun: a program that sent
   from its setup passed then and fails now. Compare those cells with care, or run them again.
5. A program can't see who sent: the call scope's ={ caller }= is not in the api (=ermine.calling()=
   is the host's). E's =e.caller= and F's =me.caller= throw NotInApi.
6. =why= can't tell a setup's write from an effect act's or an after-await write: all are
   "outside". E's "program" and F's "setup" / "act" kinds are cut from their sheets (by: memo,
   effect, call, outside; kind: run, call, outside).
7. A write's site is the first frame outside ermine's own files. With an adapter in between, every
   write in B–F is sited at the adapter's line, not the program's. A library over the api hides
   the program's sites, and a program can't add its files to the skip list.
8. A node is a plain ={ path, part }=: printed, it shows its path; written as a value, it is stored
   quietly (=edit(x, () => otherNode)=). The throwing handles of E and F are the adapters' only.
9. =open(p)= without a value makes nothing, and =edit= of a node not there throws nothing-there
   (words.ts says "made if missing", meaning the entry). So =x(v)= / =x.set(v)= after a bare
   =open(p)= throws, in every design.
10. A memo or effect at a path whose folder is missing throws nothing-there; =method= makes the
    folders. The adapters for E and F make the parent first.
11. A memo read in the same setup that made it gives undefined, not pending: it hasn't run, so its
    status isn't pending yet. F's NotReady can't fire there.
12. A pending read caught inside a memo is swallowed by the real api (the memo is done with what f
    returned). E and F say pending is sticky; their adapters remember the pending read and make the
    run pending anyway (sync only).
13. An async handler that throws after an await: nothing reports it unless the sender awaits the
    promise send gave back (send's own =then= marks it handled).
14. Small mismatches: F's =values= has read = last, the real =reads= has read = first (the same
    with no features). Taken for =answer= isn't checked (the real =method= replaces quietly). E's
    =e.path= and F's =move= of an id handle, and F's =info(node).names=, have no real word: NotInApi.
    E and F's own folder vs current dir: the real api keeps a process's own node and its cwd apart;
    both designers took them as one.
15. G: globals are one per realm, the real api is one per process. The adapter puts the latest
    process's words on =globalThis=; two G programs in one deno would share (and overwrite) them.
    A global can't know which process calls it after an await either (finding 1).
16. G: one effect can't be ended before its owner goes. Watch's unsubscribe is the adapter's flag:
    the act does nothing after, and f reads nothing on its next run (so it stops being told). The
    hidden effect stays in the graph until the program's scope goes.
17. G: a watch on a node not there must not fire, but the real effect acts with undefined. The
    hidden effect's f returns PENDING while =entries= is empty, so the effect shows as pending in
    the graph until the node comes. A node that comes holding nothing (or a derived value whose f
    gives undefined) is never told.
18. G: =x.set(v)= on a node not there needs =open= (the real =edit= throws nothing-there, finding
    9); a derived value read in the setup that made it is undefined (finding 11), which in G's words
    is the same as "not there".
19. G2, G3: the real recipe takes a returned value as the new whole value, so =d => d.push(v)=
    would write a number. "Returns nothing" is the adapter's: it drops the return. A recipe on a
    number (a draft can't change a primitive) does nothing; =set= is the word for those.
20. H: =api.open= with a path given as an array does not take it from the root (it makes nothing
    at the node's own path), so writing to a node not there needs the path as a string. The real
    api's =Node.path= doesn't round-trip through =open=.
21. K: Solid's =name= is a debug name; ermine needs a path for every node, so K gives it that
    meaning, and makes a hidden node for each unnamed signal, memo, effect and store.
22. K: no transactions in the process api, so =action= can't hold its writes, and =latest= has
    nothing to show past. No way to ask a memo to run again, so no =refresh=.
23. K: ermine's effect compares values by default, Solid 2.0's never does: K passes =equal: () =>
    false=. Its untrack is the adapter's flag over its own getters (the real api has peep per node,
    no untracked scope).
24. memo-send, E and F: a memo can't send in either (=e.call= and =me.send= are NotHere in a
    compute: the designers' rule). Their references bend: an effect on ./text whose act calls the
    service and writes a node ./loud (made by the program), and a second effect showing it. "loud"
    is then a written node, not a derived one; the check can't tell, it reads the node.
25. memo-send, G: =x.call()= in a derived value is =sendWaiting=, whose wait (service not there
    yet) is a hidden effect made inside the memo's run: owned by that run, made again at each one.
    It works; the graph shows a =.wait-N= per run that waited.
26. pending, K: the only word for "a node at a path someone else made" is =createSignal(undefined,
    { name: "/slow/value" })= (as in slow): a signal over a memo's node. =isPending= reads it.
27. shared: a process's row is at its code's path, so the same code node can't be started twice
    (taken). Two processes of one program need two code nodes holding it (lib/trial.ts =TWO=).
28. L: code ermine didn't call has no scope open, so every imported word throws there. Each of
    these fails in L and works in A (A's words are bound to the process; after an await they fall
    back to the origin's scope, finding 1):
    - after an await in a handler: =method("./on/save", async (t) => { await save(t); edit(s, …) })=
    - a promise's then: =return save(t).then((r) => edit(s, () => r))=
    - a timer: =setTimeout(() => edit(count, (n) => n + 1), 1)= (uncaught, out of nobody's call)
    - a module's top level: =const count = open("./count", 0)= above =export default= (load fails)
    - an async memo after its await: =memo("l", async () => { await null; return read(x) })= (the
      memo fails; in A the read lands untracked)
    - a listener called from outside ermine: =t.addEventListener("tick", () => edit(count, …))=, the
      event dispatched from a timer (dispatched inside the setup, it works: the setup is on the stack)
    =here()= mends the await, the then, the timer and the listener, kept where its scope outlasts
    the use (the call's for the await and the then; the setup's for a timer). A module's top level
    has none to keep.
29. L, here(): written in a call's scope after its await, a write carries the call's metadata
    (caller, handler, call), but the call's record ended when the handler returned its promise, so
    it doesn't hold the write: =why= says =by.replaced= (the handler), not =by.call=. A's write
    there says =by.outside= with a fallback note. Neither says "this call".
30. L: the registry is the adapter's: the real api has no way to ask "which process is this scope
    in". It walks the scheduler's =parent= links to a scope it was told about. Two processes in one
    realm (the shared task) each find their own: the thing G–K's globals can't do (finding 15).
31. components (the first renderer, before 10-25's reactive one): =runWithScope= opens a scope
    untracked, so a component run in a plain scope of its own can't track. A component has to be
    a computer to be reactive: now an early effect (=api.early=), the only effect that runs at
    once, so =h= has its first render to give back. Its name is the harness's (=.jsx-Counter-N=):
    the api has no unnamed computer.
32. components, E and F: a component can't be drawn where it is made. E's act =e= can't place a
    handler (NotHere), F's act =me= can't answer, and a draw happens in an act; their counter.jsx
    is a factory called in the setup, giving back a view the act draws with its own e / me.
33. components: a tree drawn in an act is drawn again at each act; what the last act made goes
    before it, so its instances (and their handlers) go and are made again, under the same names
    (by place). A tree shown once from the setup keeps its instances for the program's life. An
    instance's first run that writes a node it read (=open("./a/count", 0)= then =read=) is stopped
    and acts later, outside =h=: the harness tells a first render from a re-render by being inside
    =h=, not by counting acts.
34. --import-map takes the place of deno.json's imports (not merged), so "ermine" importable
    means a map with the repo's imports copied in (lib/importmap.ts).
